# Upgrading to EQL 3.1

`3.1.0` is a minor release. It changes three things in the `eql_v4` surface
that a caller can meet without changing any SQL: which terms a text search
query must carry, which block ORE ciphertext the `_ord_ore` and
`text_search_ore` domains hold, and the shape every order term must have. **The `eql_v3` bundle is unchanged, byte for
byte.** If you install only `eql_v3`, nothing here applies to you.

Both changes land through Stack Encrypt as well as through the SQL: with
`3.1.0`, Stack Encrypt produces `eql_v4_text_search` and every block ORE
type (`_ord_ore` and `text_search_ore`), so a value written by it carries the
terms this release's `eql_v4` expects. The notes below are for anyone who
builds `eql_v4` payloads by hand, or who stored `eql_v4` block ORE terms
before this release.

## TL;DR

1. An `eql_v4` text search query carries only the term its operator reads,
   and an operator reading a term the query does not carry **raises**
   (`invalid_parameter_value`) instead of matching nothing or everything —
   [U-001](#u-001-a-text-search-query-carries-only-the-terms-its-operator-reads).
2. The `eql_v4` block ORE term is ore-rs's 6-bit scheme, compared by a new
   comparator named `ore_block_v2`. It **refuses** the 8-bit terms the
   previous `eql_v4` bundle compared; rows and queries holding them must be
   written again through Stack Encrypt —
   [U-002](#u-002-the-block-ore-term-is-ore-rss-6-bit-scheme).
3. An `eql_v4` order term is **one hex string**, `"ob": "0202…"` rather than a
   one-element array, and every `eql_v4` domain with an order term **checks
   its prefix** when it is written. A database that installed an earlier
   `eql_v4` bundle must drop its stored order domains before installing this
   one —
   [U-003](#u-003-an-order-term-is-one-hex-string-checked-when-it-is-written).

## Upgrade notes

### U-001: A text search query carries only the terms its operator reads

**What changed.** `eql_v4.query_text_search` and
`eql_v4.query_text_search_ore` required every term of the type: `hm` for
`=`, `op` (or `ob`) for the orderings and `bf` for `@@`. They now require at
least one. Each operator reads one term, and the extractor it reads through
raises when the query does not carry it, carries it as JSON `null`, or
carries an empty array:

```text
ERROR:  query_text_search value has no "hm" term, the term = <> compare
SQLSTATE: 22023 (invalid_parameter_value)
```

The message names the domain, the term and the operators that read it,
never the operand. The raise happens wherever the operand is read, so a
statement whose predicate is never reached (a generic plan over an empty
table, say) returns no row and no error.

**Why.** Text shorter than one 3-gram has no match term, so with every term
required a search column could never be asked `name = $1` or `name < $1` for
such text, although both have an answer. And a term that is present but
unreadable must not become a silent miss: before, a missing term read as
`NULL`, which compares equal to nothing and matches no row.

**Who is affected.** A caller that builds query operands by hand, or that
checks them against the domain CHECK. Stack Encrypt builds the query for the
operator's index and carries that term alone; nothing changes for its
callers. Stored values are untouched: a stored search value still carries
every term, and a row stored before this release is found exactly as before.

**What to do.** Nothing, for stored data. If you build a text search query
yourself, carry the term the operator reads; carrying the others as well is
still valid. Do not pass `null` or `[]` for a term you lack: omit it, and ask
only through operators whose term you carry. If you handled "no result" from
a query with a missing term, expect an error now.

**Verification.**

```sql
-- A query carrying one term is a valid operand (was refused by the CHECK):
SELECT '{"v": 4, "i": {"t": "users", "c": "name"}, "hm": "00"}'
  ::jsonb::eql_v4.query_text_search;

-- A query carrying no term is still refused by the CHECK (23514):
SELECT '{"v": 4, "i": {"t": "users", "c": "name"}}'
  ::jsonb::eql_v4.query_text_search;
```

Then, on a table with at least one row, `WHERE name < $1` with the `hm`-only
operand above must fail with SQLSTATE `22023` and the message naming `op`.

### U-002: The block ORE term is ore-rs's 6-bit scheme

**What changed.** The `ob` term of every `eql_v4` block ORE domain is now
one ciphertext of ore-rs's 6-bit block ORE: the fixed-width scheme for
numbers, the chained scheme for text, which pads the text to a power-of-two
length bucket of at least 16 bytes. The v4 bundle names its block ORE objects
`ore_block_v2` (`eql_v4_internal.ore_block_v2_term`,
`eql_v4_internal.compare_ore_block_v2_term`) and compares them with a new
comparator that checks each term's shape before comparing, then runs the
same number of statements whatever the terms hold. It raises on:

- a term that is not a 6-bit block ORE ciphertext, the previous 8-bit layout
  included: `Malformed ORE block term: N bytes`;
- two terms of different schemes (fixed-width against chained): `ORE block
  terms of different schemes`;
- two chained terms padded under different policies: `ORE block terms padded
  under different policies`.

The `eql_v3` bundle keeps the 8-bit scheme under `ore_block_256`, unchanged.

**Why.** The 6-bit scheme is what Stack Encrypt derives, and with it Stack
Encrypt produces the block ORE types (`IntegerOrdOre`, `SmallintOrdOre`,
`BigintOrdOre`, `RealOrdOre`, `DoubleOrdOre`, `TextOrdOre`,
`TextSearchOre`) for the first time. One comparator per scheme, with the
scheme in the name, keeps a v3 term and a v4 term from ever being compared
by the other's rules.

**Who is affected.** No Stack Encrypt release wrote an `eql_v4` block ORE
term before this one: the block ORE types were not producible. So a v4
`_ord_ore` or `text_search_ore` row holding an 8-bit term exists only where
it was written by hand, or with cipherstash-client's ORE indexer, against
the earlier `eql_v4` bundle, which compared such terms. If you have such
rows, or query operands or `eql_v4.between` ranges built that way, they are
refused by this release's comparator with the first error above. They are
never ordered wrongly: a refused term is an error, not a result.

**What to do.** Where such rows exist, write the affected columns again
through Stack Encrypt, which derives the 6-bit term for every block ORE
type, and build every block ORE query and range operand through it as well.
Do this before creating or rebuilding a functional index over
`eql_v4.ord_term_ore(col)`: an index build compares every row, so one
8-bit term in the table fails the build. Installs that never held an
`eql_v4` block ORE term, and installs whose block ORE domains are disabled
(no operator class), have nothing to do.

**Verification.**

```sql
-- The v4 bundle names its block ORE objects by the scheme:
SELECT p.proname
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'eql_v4_internal' AND p.proname LIKE '%ore_block%'
ORDER BY 1;   -- ore_block_v2 names only; no ore_block_256

-- Every stored term in a block ORE column is one the comparator accepts:
-- this compares each row's term with itself and raises on a term it refuses.
SELECT count(*) FROM users WHERE age <= age;   -- equals count(*), no error
```

### U-003: An order term is one hex string, checked when it is written

**What changed.** An `eql_v4` block ORE term (`ob`, and the `lo` and `hi`
bounds of a `query_*_range_ore` operand) is one JSON string, the lowercase
hex of the whole ore-rs ciphertext:

```json
{"v": 4, "i": {"t": "users", "c": "age"}, "c": "…", "ob": "02020006…"}
```

It was a one-element array (`"ob": ["02020006…"]`). Every `eql_v4` domain
that carries an order term now checks its shape in its CHECK, stored, query
and range alike:

- `ob` must be a string starting `0202` (ore-rs's fixed-width engine) or
  `0203` (its chained engine);
- `op` must be a string starting `00` or `01`, the OPE term's carry byte.

A value of any other shape is refused when it is written or cast,
SQLSTATE `23514` (`check_violation`), before any comparison reads it. The
check reads the prefix only, so it costs the same whatever the term's
length. The comparator still checks the rest of a block ORE term's
structure, as U-002 describes.

In Rust, eql-bindings holds these fields as Stack Encrypt's own terms, typed
by the plaintext they order: `DateOrdOre::ob` is a
`stack_encrypt::sem::OreBlockTerm<Date>` and `IntegerOrd::op` an
`OpeTerm<i32>`. Reading a payload checks the term's structure, so a
malformed term, or a term of the other scheme, is refused there too.

**Why.** The array was cipherstash-client's shape for its 8-bit block ORE,
which held several terms for text. An ore-rs term is always one, and the
array added a level that said nothing and checked nothing. Checking the
prefix at write time catches an EQL v3 term or a term of the wrong scheme
where it enters the database, not at the first query that reads it.

**Who is affected.** No Stack Encrypt release wrote an `eql_v4` order term
in the array shape: the ordered types became producible in this release. A
program that builds `eql_v4` payloads by hand must write `ob` as a string.

A database that installed an earlier `eql_v4` bundle, such as the one
attached to the Go module's `v0.1.0-alpha.1` release, keeps its stored
`public.eql_v4_*` domains when this bundle is installed: they are created
only if they do not exist. Those domains still require `ob` to be an array
and do not check `op`, so they refuse every `ob` this release writes.

**What to do.** In a database that installed an earlier `eql_v4` bundle,
drop the stored order domains before installing this one, so the install
creates them with the new CHECKs. A domain a column uses cannot be dropped;
move such a column to `jsonb` first and back afterwards, or write it again
into a new column:

```sql
-- Lists the stored eql_v4 domains that carry an order term.
SELECT t.typname
FROM pg_type t
JOIN pg_constraint c ON c.contypid = t.oid
WHERE t.typnamespace = 'public'::regnamespace
  AND t.typname LIKE 'eql\_v4\_%'
  AND (pg_get_constraintdef(c.oid) LIKE '%''ob''%'
       OR pg_get_constraintdef(c.oid) LIKE '%''op''%');

-- For each one no column uses:
DROP DOMAIN public.eql_v4_integer_ord_ore;
```

The query operand domains (`eql_v4.query_*`) are recreated by every
install, so they need nothing.

**Verification.**

```sql
-- The stored domain refuses the array shape:
SELECT '{"v": 4, "i": {"t": "t", "c": "c"}, "c": "x", "ob": ["0202"]}'::jsonb
  ::public.eql_v4_integer_ord_ore;
-- ERROR:  value for domain eql_v4_integer_ord_ore violates check constraint
```

## Verification checklist

- [ ] The `eql_v4` install reports `3.1.0` (`SELECT obj_description('eql_v4'::regnamespace, 'pg_namespace')`).
- [ ] A one-term `eql_v4.query_text_search` operand casts (U-001).
- [ ] `eql_v4_internal` lists `ore_block_v2` objects and no `ore_block_256` (U-002).
- [ ] Every `_ord_ore` / `text_search_ore` column passes the self-comparison scan (U-002).
- [ ] The stored `eql_v4` order domains require a hex string with a scheme prefix (U-003).
- [ ] Grants and functional indexes have been re-applied after the install
      ([U-002 in the 3.0.5 guide](./v3.0.5.md#u-002-grants-and-dependent-objects-do-not-survive-an-install)).

## Rollback

Installing the 3.0.6 bundle reverses both notes at the SQL, and neither
reversal misreads data:

- U-001: the 3.0.6 CHECK requires every term again, so a one-term query is
  refused by the domain (SQLSTATE `23514`) rather than answered.
- U-002: the 3.0.6 v4 comparator expects the 8-bit layout, so a 6-bit term
  written under 3.1.0 is refused as malformed, exactly as the 8-bit terms are
  under 3.1.0. Rolling back a database that holds 6-bit terms therefore
  means rewriting those columns too, with a Stack Encrypt that derives the
  8-bit term, and no release does. Decide before writing block ORE rows under
  3.1.0 whether a rollback must stay possible; if it must, hold off on the
  block ORE domains and order through the `_ord` / `_ord_ope` domains, whose
  terms this release does not change.

Any install, in either direction, re-runs `DROP SCHEMA … CASCADE`, so grants
and dependent objects need re-applying afterwards.
