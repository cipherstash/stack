## Change risk: Changes or verification required

**Impact if something goes wrong:** high · **Verification confidence:** low · `c806cfd83c..37c32967ba`

Moves the EQL release pipeline (SQL bundle, docs bundle, crate, postgres-eql image, prerelease npm publish) from the dead packages/eql/.github/ directory into the root workflows, gated by a switch derived from FROZEN_PUBLISHERS so it stays inert until the Phase-5 cutover. Two things change today. release.yml, the single npm publishing workflow for all JS and FFI packages, gains workflow_dispatch and a `classify` job that every publish job now depends on. The root rebuild-docs.yml is deleted; per the commit message it never fired. The most material risk is that a dispatch against any branch reads both the arming switch and the release-gate from that branch's own code, so whether the pipeline is inert, and what a prerelease publishes, is decided by unreviewed code. No publish job declares a GitHub `environment:`. Most of the remaining risk sits in the first armed run: npm publishes first and cannot be undone, the other four artefacts follow in separate builds that have never run here, and release-plz publishes the crate on its own trigger without checking the npm release. Static workflow tests cover the gating wiring. None were run and no CI results were available.

### Failure scenarios

**FS-1 · A dispatch against an unmerged branch decides for itself whether EQL publishes and what it publishes** (high impact, plausible)

- Trigger: Someone who can dispatch workflows (by mistake, as an insider, or with a compromised token) runs release.yml or release-plz.yml against a branch. The branch's HEAD subject is `chore(release): …`, its package.json pins X.Y.Z-alpha.N, and it deletes the @cipherstash/eql FROZEN_PUBLISHERS entry or otherwise edits release-gate.mjs. After the cutover, the deletion is no longer needed.
- Mechanism: `classify` sets mode=prerelease for any non-main ref with that subject (release.yml:84-91). `eql-armed` and `gate` run `node scripts/eql-pipeline-armed.mjs` and `node scripts/release-gate.mjs` from that ref's checkout (release.yml:151, 192), so both answers come from the branch under release. The prerelease jobs then hold contents:write and id-token:write. They create the eql-<V> release and the eql-typescript-v<V> tag, publish the npm package built from the branch, force-update release/eql-<V> and dispatch release-plz.yml there, which reads the switch from that branch again (release-plz.yml:44,73). No publish job declares an `environment:`, so no required reviewer stands between a dispatch and a publish. CODEOWNERS governs merges, not dispatches. Before this change release.yml had no workflow_dispatch.
- Consequence: Before the cutover, npm and crates.io trusted publishing do not name this repository, so the registry publishes should fail. Public eql-<V> GitHub releases with SQL assets, tags and a release branch can still be created in cipherstash/stack from unreviewed code. After the cutover, an @cipherstash/eql prerelease (SQL install bundle embedded) and the eql-bindings crate can be published from an unmerged branch, with valid provenance naming this repository. Publishing cannot be undone, and the SQL is applied to customer databases.
- Affects: .github/workflows/release.yml (JS, FFI and EQL npm publishing), .github/workflows/release-plz.yml (eql-bindings crate), @cipherstash/eql npm package, eql-bindings crate on crates.io, eql-<V> GitHub releases (SQL bundle, docs) and postgres-eql image, scripts/release-gate.mjs FROZEN_PUBLISHERS
- Evidence: `.github/workflows/release.yml:39-43`; `.github/workflows/release.yml:76-125`; `.github/workflows/release.yml:132-192`; `scripts/eql-pipeline-armed.mjs:24-37`; `.github/workflows/release.yml:642-754`; `.github/workflows/release.yml:756-786`; `grep -n 'environment:' .github/workflows/release.yml .github/workflows/release-plz.yml .github/workflows/release-postgres-eql-image.yml`; `.github/workflows/release-plz.yml:44-85`; `scripts/release-gate.mjs:142-149`
- Existing verification: eql-pipeline-armed.test.mjs pins which jobs carry the `eql-armed` condition. It checks condition text and does not examine which ref the switch is read from. [exists_not_run]; workflow-dispatch-job-conditions.test.mjs evaluates job conditions on a dispatch event (changed in this diff; contents only skimmed). [exists_not_run]
- Missing verification: No check that a prerelease publish can only come from a reviewed or protected ref; No visibility of repository settings (who can dispatch, rulesets on release/** and chore(release) branches, environment protection)
- Mitigation: Put the publishing jobs (prerelease-eql-*, release, publish-ffi, release-plz `release`, image build) behind a GitHub environment with required reviewers and a deployment-branch policy, or restrict prerelease dispatch to a protected branch pattern. Optionally read the arming switch from the default branch rather than the dispatched ref. Confirm the npm and crates.io trusted-publisher entries pin the environment as well as the workflow filename.

**FS-2 · First armed run publishes npm first, then other artefacts may never follow, or the crate ships alone** (medium impact, plausible)

- Trigger: The first push to main after the FROZEN_PUBLISHERS entry is deleted (Phase-5 cutover), or any later EQL release in which a downstream build fails, or the gate and the switch disagree.
- Mechanism: `release` runs `changeset publish` (irreversible) before eql-sql, eql-docs and eql-image, which then do their own cold builds on Blacksmith runners (release.yml:508-556; _build-eql-sql.yml:80-87). None of these jobs has executed in this repository. Documented prerequisites that no workflow can check in advance (a GPG_PRIVATE_KEY secret and GHCR write access) are missing today (AGENTS.md:358-360). release-plz.yml publishes the crate on its own push trigger, gated only on `eql-armed` and not on the npm release succeeding (release-plz.yml:26-44, 75-78). The production npm publish is held by `gate`, not by `eql-armed`, and AGENTS.md:343-355 states nothing asserts the two agree.
- Consequence: Version V of @cipherstash/eql reaches npm with no matching eql-V SQL release, docs bundle or postgres-eql image. Or eql-bindings V reaches crates.io while the npm release was blocked. The single-version promise across five artefacts breaks, nothing reports it as a release failure, and recovery means hand-dispatching or cutting a new version.
- Affects: .github/workflows/release.yml (JS, FFI and EQL npm publishing), .github/workflows/release-plz.yml (eql-bindings crate), .github/workflows/release-postgres-eql-image.yml (ghcr.io/cipherstash/postgres-eql), _build-eql-sql.yml / _build-eql-docs.yml, @cipherstash/eql npm package, eql-bindings crate on crates.io, eql-<V> GitHub releases (SQL bundle, docs) and postgres-eql image
- Evidence: `.github/workflows/release.yml:508-556`; `.github/workflows/_build-eql-sql.yml:80-124`; `.github/workflows/release-plz.yml:26-78`; `AGENTS.md:358-362`; `AGENTS.md:343-355`
- Existing verification: eql-pipeline-armed.test.mjs drives the switch in both states as a unit, but not the workflows end to end. [exists_not_run]; eql-summary job reports per-job results in the run summary (an observability aid, not a check). [exists_not_run]
- Missing verification: No dry run of the armed production chain (eql-sql, eql-docs, image) before the cutover; No assertion that the crate publish requires, or follows, a successful npm publish of the same version; No test that `gate` and `eql-armed` agree on whether @cipherstash/eql is publishable
- Mitigation: Before the cutover, exercise the armed chain with a prerelease identity on a protected branch. Provision the GPG key and GHCR access first. Gate release-plz's `release` on the npm version already being on the registry, or trigger it from release.yml after `release`. Add a test asserting that release-gate and eql-pipeline-armed agree.

**FS-3 · SQL on the GitHub release and in the image is rebuilt from source rather than taken from the npm tarball** (medium impact, speculative)

- Trigger: An armed production or prerelease EQL release, built with a different `rust latest` toolchain or environment than the one that ran `pnpm run version`.
- Mechanism: The npm package ships the SQL committed by the version hook and checked by verify-release-assets.mjs. _build-eql-sql.yml instead regenerates SQL with `mise run --force build --version` at publish time (lines 80-87), and the image workflow builds it a third time. The version stamp will match in every case. AGENTS.md:427-431 records that nothing proves regeneration reproduces the published bytes.
- Consequence: The eql-V GitHub release asset or the image can carry SQL bytes that differ from npm's under the same version and stamp. A digest comparison against the npm release manifest fails, or a different function body is installed depending on which channel a customer used.
- Affects: _build-eql-sql.yml / _build-eql-docs.yml, @cipherstash/eql npm package, eql-<V> GitHub releases (SQL bundle, docs) and postgres-eql image
- Evidence: `.github/workflows/_build-eql-sql.yml:80-124`; `AGENTS.md:427-431`; `.github/workflows/release-postgres-eql-image.yml:15-100`
- Existing verification: eql-sql-asset-freshness.test.mjs compares the version and stamp across the in-tree artefacts, not the bytes rebuilt in CI. [exists_not_run]
- Missing verification: No digest comparison between the rebuilt SQL and the committed or npm-bundled release-manifest before attaching
- Mitigation: Attach the committed packages/eql/packages/eql/sql bundle (or verify the rebuilt file's digest against its release-manifest.json) instead of shipping a fresh build.

### Recommended controls

- Review release.yml's `classify` and prerelease jobs, and release-plz.yml's dispatch trigger, for who can start a credentialed publish and from which refs. (review_focus; FS-1, VG-1)
- Add a protected GitHub environment (required reviewers, deployment-branch policy) to every publishing job, and bind the npm and crates.io trusted publishers to it. (other; FS-1)
- Add a test asserting `release-gate.mjs` and `eql-pipeline-armed.mjs` agree on @cipherstash/eql, and that release-plz's publish depends on the npm version being on the registry. (test; FS-2, VG-2)
- Before deleting the FROZEN_PUBLISHERS entry, provision GPG_PRIVATE_KEY and GHCR access, rehearse with a prerelease identity, and write down how to hand-dispatch the SQL, docs and image jobs if they fail after npm has published. (rollback_plan; FS-2, VG-2)
- Verify the rebuilt SQL digest against the committed release-manifest.json before attaching it to the GitHub release or baking it into the image. (compatibility_check; FS-3)
- Run `pnpm test:scripts` (or confirm CI ran it green) on head before merge. (test; VG-3)
