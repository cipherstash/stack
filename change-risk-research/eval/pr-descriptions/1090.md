# fix(stack-auth)!: one CTS token per provider JWT in OidcFederationStrategy

## Summary

Fixes a bug where a server sharing one authentication strategy across users could send user B's encryption requests with user A's access token. Values encrypted with an identity restriction could then be bound to A, leaving B unable to decrypt them. The strategy now asks for the caller's identity token on every request and caches CipherStash access tokens separately for each distinct identity token.

## Changes

- **Token caching:** `OidcFederationStrategy`, which exchanges an OpenID Connect (OIDC) provider's JSON Web Token (JWT) for a CipherStash access token, now caches by a SHA-256 digest of the entire JWT. Each entry keeps the existing refresh, concurrent-request deduplication, denial, and cancellation behavior.
- **Stored tokens:** Adds optional `Token::federated_from` metadata identifying the JWT that produced a token. Tokens from another JWT, expired tokens, and older tokens without this metadata cannot be reused for the current caller.
- **Cache settings:** Defaults to 1,024 entries and evicts the least recently used entry when full. Rust, Node, and Go expose cache-capacity settings; zero disables caching. Evictions are logged at debug level.
- **Node guidance:** Requires one strategy per request or per user, with the request captured in the `getJwt` closure. Updates package documentation, declarations, examples, and the affected customer skills.
- **Release impact:** Changes the provider and token-store contracts and adds optional token JSON metadata. The Rust change is marked breaking; the `@cipherstash/auth` changeset is a minor release because the `getJwt` contract changes.

## Review notes

- **Node callers must capture the right request.** The native binding invokes `getJwt` outside the `getToken()` caller's `AsyncLocalStorage` scope. A long-lived strategy that reads the current request from that scope can still select the wrong user; the per-JWT cache cannot fix an incorrect provider result.
- **Cache keys use the whole JWT.** The client cannot verify JWT claims itself. A forged token claiming another user's identity gets its own cache entry and exchange refusal. Rotating a user's JWT therefore requires a fresh exchange.
- **Rust and Go can share a strategy across users** when the provider identifies the caller on every request. Go passes the token call's context to the provider.
- **Token stores retain their single-slot interface.** `load` receives no key, so a shared store returns at most one user's token at a time. Stores can use `federated_from` when writing per-user entries.
