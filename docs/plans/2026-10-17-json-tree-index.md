# The EQL v4 `json_tree` index: node-local entries, a token chain, and exact containment

**Status:** the design and implementation record of the EQL v4 `json_tree` index, Stack Encrypt's JSON index. First written as a design with a phased plan to prove it; implementation notes are appended at the end as each phase lands
**Date:** 2026-10-17
**Author:** Dan Draper (with Claude assistance)
**Relates to:** #1231 (containment matches across array elements), #1209 (`Contains`, `ContainedBy`, `AtPath` declared), ADR-0009 (operators select the index), system ADR-0002 (EQL v4 by producer), `packages/eql/docs/plans/stevec-envelope-key-header-rfc.md` (the v3 envelope), `docs/plans/2026-10-04-plan-builder.md` ("The JSON index" under Additions)
**Prototypes:** `2026-10-17-json-tree-index/` beside this file, three SQL files that run on a stock PostgreSQL 16 with no extension

> **Note (2026-10-22).** The stored form this document designs has changed twice since, and the implementation notes at the end record each change. As of Phase 3b a stored entry carries only `s`, `c`, `p` and `op`. The value selectors live only in the stored projection `q`. The group tags `n` and `g`, the wrapped token `w` and the stored ordinal (`i` here, `o` in the code) are gone. A child's token is derived from its parent's token and its ordinal, not its label, and the walk probes ordinals until the first miss. The sections below are kept as written, with short dated notes where they would otherwise mislead.

## Summary

Stack Encrypt has no JSON index yet. The operators exist (#1209 merged `op::Contains`, `op::ContainedBy` and `op::AtPath<Op>` on `next`), the plan-builder document reserves `Json: Index<Value>` as "a new core operation", and EQL v4 has a storage-only `public.eql_v4_json` but "no SteVec bindings yet". The v4 JSON wire format is therefore unconstrained by anything shipped. This document records what to build and the phased plan that proves it, and the implementation notes at its end record what each phase built.

Three changes to the v3 SteVec design, taken together:

1. **One entry per JSON node, encrypting only that node.** A path entry today encrypts its whole subtree, so a document's ciphertext is O(size × depth) and the root entry alone is the size of the document. Under this proposal an entry's ciphertext holds the node's edge label, its kind and, for a scalar, its value. Total ciphertext is O(size). The separate value entry is folded into the same entry as a second selector field, halving the entry count.
2. **A token chain links a node to its children, and the server can walk it from a query key.** Each node has a secret 16-byte token. The client derives a path's token from the index key and the path alone. Each child entry stores a *parent tag* (a hash of the parent's token) and its own token *wrapped* under the parent's token. A `WITH RECURSIVE` query that is handed one start token finds that node's children by tag, unwraps their tokens, and recurses, in core SQL (`sha256`, bytea XOR). Without the token the tags and wraps are unlinkable random bytes. This is what makes node-local ciphertexts usable: `doc -> '$.a'` on an object returns the subtree's entries in one round trip, and the client reassembles the object. The prototype in `token-chain.sql` does exactly this. By default the chain starts one level down: the root entry carries the whole document, as in v3, and the top-level fields are the chain heads, so no query can ever hand the server a token for the whole column ("The sealed root", decided 2026-10-18).
3. **Exact containment, closing #1231.** Every entry under an array element carries the element's *group tag*. Containment stays a GIN-indexed `jsonb @>` over the selector sets, which is a necessary condition, and gains a recheck, run only on the rows the index returned and only when the needle has an array element that is a container, that requires each needle element's selectors to come from one stored element. The prototype in `containment-oracle.sql` agrees with PostgreSQL's `jsonb @>` on 29 of its 31 cases, including the six cross-element cases where today's selector containment is wrong; the other two are simulation artefacts the file lists. The issue's "plausible" false negative (`'["a"]' @> '"a"'`) is verified real and fixed by letting a root-scalar needle carry two selector sets.

Everything here works on standard PostgreSQL, as a non-superuser, with no extension: the SQL uses `sha256(bytea)` (core since 11), `get_byte` / `set_byte`, recursive CTEs and the `jsonb_path_ops` GIN operator class.

**It ships as a new domain type in EQL v4, not as the v4 SteVec (decided 2026-10-18).** The scheme gets its own column domain, query domain and entry domain beside `public.eql_v4_json` and whatever v4 port of the v3 SteVec `json_search` type may follow, and it shares no wire shape or SQL with them. Two reasons. It must not block the v4 release: a new domain is additive and can land in any 4.x. And this is what the domain-per-scheme design of EQL v3, carried into v4, was for: a new encryption scheme is a new domain type, with its own CHECK, operators and functions, and never a new EQL version. The domain names below use the placeholder `eql_v4_json_tree`; the final name is a Phase 4 decision. (Taken on 2026-10-25: the domains carry the names EQL v3 gives its searchable JSON document, `public.eql_v4_json_search`, `public.eql_v4_json_entry`, `eql_v4.query_json` and `eql_v4.query_json_leaf`, with the target `JsonSearch`; see "Where it is" under the implementation notes. Later sections keep the placeholder names they were written with.)

## Where we are

### The v3 SteVec, as cipherstash-client 0.42.3 produces it

Read from the crate source (`src/encryption/json_indexer/`), not from memory:

- `flatmap_json` walks the document. Every node emits a **path entry** `{s, c, op?}` and a **value entry** `{s, c}`. `s` is a 16-byte keyed Blake3 MAC of the canonical JSONPath (`$['a'][*]['x']`), under a per-column `prefix`. The value entry's `s` is `MAC(6-byte type tag ‖ path token ‖ canonical value)`; containers get a tag only (`MAP0{}`, `ARRY[]`). `op` is a CLLW OPE term on string and number leaves only. A value entry's `c` encrypts a fixed three-byte sentinel.
- Arrays are indexed under `ArrayIndexMode`: wildcard `[*]`, item `[@]` and positional `[n]` selectors, any combination. Under the wildcard every element of an array shares one path selector, which is the root of #1231.
- The path entry's `c` is the AEAD of the node's **whole subtree** as a `Plaintext`. The root entry (index 0) is the whole document; decryption of a document reads only the root (`into_root_record_with_nonce`).
- Since the envelope RFC: one `KeyHeader` `h` per document (iv, key tag, descriptor, keyset id), entries carry raw AEAD output, nonce `= s[..12]`, AAD `= descriptor ‖ tag ‖ s`, AES-256-GCM-SIV. SIV is what makes equal selectors (sibling array elements with equal values) safe: the cipher degrades to determinism rather than breaking.
- The SQL (`packages/eql/src/v3/json/`): `@>` is `to_ste_vec_query(a)::jsonb @> to_ste_vec_query(b)::jsonb`, where `to_ste_vec_query` projects each entry to `{s}`; a GIN `jsonb_path_ops` index on that expression serves it. `->` by selector grafts `h`, `i`, `v` onto the matched entry so it is self-contained decryptable. `jsonb_array_elements` and `jsonb_array_length` rely on a per-entry `a` flag.

### What Stack Encrypt has

- `op::Contains`, `op::ContainedBy`, `op::AtPath<Op>` and the arity `Pathed<A>` (PR #1209, on `next`). `TermFor<Contains>` is implemented for every `QueryTerm`, so the containments are declared **exact**, and the issue keeps that declaration on purpose. No `Supports<Contains, _>` impl exists; a query with these operators does not compile.
- `IndexSpec` is `Equality | Match | Ore | Ope`. The plan-builder document reserves `"json"` as the fifth key and describes the operation: "it mints one document key and seals every entry under it, a new core operation (one generate request, a fulfilment that seals N entries with selector-derived nonces)".
- The PRF: `KeysetCipher::prf()` is an `HmacSha256Prf` keyed by the keyset's index key, with PAE-framed domains per term kind (`sem/mod.rs`). Selectors and tokens derive through it. Nothing is byte-compatible with cipherstash-client, by design.
- Leaves seal with vitaminc's `Aes256Cipher`, AES-256-GCM with a random nonce. There is no GCM-SIV in the dependency tree. The JSON operation needs a deterministic nonce under one document key, so nonce uniqueness has to hold by construction (see "Keys, nonces and AAD").
- The data plan (`dynamic`) and the Go guest spell indexes as `IndexSpec`; the match index already needed a wire form for its options, and the JSON index will too (plan-builder Additions, item 7).

### What EQL v4 has

ADR-0002: v4 is the v3 SQL rendered under `eql_v4` names, for values Stack Encrypt writes. `eql-bindings::v4` exists on `next` with `public.eql_v4_json` as `{v, i, c}` storage only. `v4/mod.rs` says "v4 has no SteVec bindings yet; those follow in `@cipherstash/eql` 4.0". The build renders `src/v3/**` as both bundles, so a v4-only JSON surface is a build change as well as new SQL (see "Where it lands").

## Goals and constraints

- **Security.** No new leakage beyond what the selectors already announce, except where exact containment needs it, and then the minimum. Ciphertext equality must not reveal plaintext equality anywhere the selectors do not already. Nonce reuse under one key must be impossible by construction, since AES-GCM, not SIV, is what the engine has.
- **Speed.** `Contains` (`@>`) stays a GIN probe; `ContainedBy` (`<@`) has no index, as in v3 (see "`ContainedBy`" under section 3). Scalar extraction stays one entry. Encryption cost drops with depth, because no byte is encrypted twice.
- **Size.** Remove the O(size × depth) subtree duplication. Halve the entry count. Do not grow the per-entry constant by more than the duplication saves on a flat document.
- **Standard PostgreSQL.** Core functions only, no extension, no superuser. Supabase and every managed Postgres EQL supports today.
- **Fits the engine's shape.** A `Json` index implementing `Index<Value>`, one `generate_keys` request, `Supports<Op, In>` for the operators #1209 declared, a wire form for its options, EQL's v4 JSON type as the `EncryptFrom` that frames it (plan-builder decision 5 and "EQL v4 types as field targets").

## Design

### 1. One entry per node, node-local ciphertext

The flattening is unchanged in what it visits: every node, with arrays indexed under the wildcard path. What each node emits changes:

| field | content | present on |
|---|---|---|
| `s` | path selector: `PRF(json/selector ‖ column, canonical wildcard path)`, 16 bytes | every entry |
| `vs` | value selector: `PRF(json/value ‖ column, kind tag ‖ s ‖ canonical(value))`, 16 bytes; containers contribute the tag only, as today | every entry |
| `p` | parent tag, `H("p" ‖ iv ‖ t(parent))[..16]` | every entry but the root |
| `w` | wrapped token, `t(node) XOR H("w" ‖ iv ‖ t(parent) ‖ c)[..16]` | every entry but the root |
| `n` | own group tag, `H("g" ‖ iv ‖ t(node))[..16]` | array elements that are containers |
| `g` | enclosing group tag: the `n` of the nearest enclosing array element | every entry inside an array element that is a container |
| `i` | the child's ordinal under its parent, in the clear, when parent tags are position-keyed (see "Position-keyed parent tags") | every entry but the root |
| `c` | `AEAD(k_doc, nonce(s, j), aad, label ‖ kind ‖ scalar)`: the edge label (object key or array index), the node kind, and for a scalar its value; nothing else | every entry |
| `op` | the leaf ordering term, as today, on string and number leaves | leaves that order |

`t(node)` is the node's token (next section). `iv` is the document key's IV from the header `h`, already public, reused as a per-document salt. `j` is the entry's ordinal in `sv`.

The value entry and its sentinel disappear: `vs` sits on the node's own entry. The entry count halves. `a` disappears: `n` marks an array element, and the chain enumerates an array's elements.

> **2026-10-22:** of the fields in this table a stored entry now keeps `s`, `p`, `c` and `op` (Phase 3b). `vs` moved to the stored projection `q` (Phase 3 stored it, Phase 3b removed it from the entries), and `w`, `n`, `g` and the ordinal are not stored.

What the client gets back for a scalar path (`doc -> 'sel'` where the leaf is a string) is unchanged in shape: one entry, decryptable with the grafted `h`, its own `s` and `c`, and its ordinal `j` (grafted by the extractor, as `h` is today). For a container path the client gets the subtree's entries and rebuilds the value from each entry's decrypted `(label, kind, scalar)` and the depth the walk reports. Whole-document decryption is one AEAD on the root entry when the sealed-root option (next section, on by default) is set, and otherwise the same walk, run by the client over the whole `sv` with the root token it can derive itself.

### 2. The token chain

```
t(root)        = PRF(json/token ‖ column, "$")[..16]                 client only
t(child)       = H("t" ‖ t(parent) ‖ 0x01 ‖ key)[..16]               object member
t(child)       = H("t" ‖ t(parent) ‖ 0x02 ‖ LE64(index))[..16]       array element
p(child)       = H("p" ‖ iv ‖ t(parent))[..16]                        stored
w(child)       = t(child) XOR H("w" ‖ iv ‖ t(parent) ‖ c(child))[..16] stored
```

> **2026-10-22:** superseded by Phase 3b. A child's token is `H("t" ‖ t(parent) ‖ LE32(o))`, keyed by its ordinal rather than its label, and nothing stores it: the server derives it as it walks, so there is no `w`, no unwrapping and no XOR, and the parent tag is the position-keyed one below. The client can then derive a token only for a chain head and the array positions that directly follow it, and sends gates for the rest of a path. The recursive query, the paragraph on the mask, and "Wildcard paths" below describe the original design.

`H` is SHA-256. Only `t(root)` needs the index key; everything below it is hashing, so the server can do its half with core functions. The tokens are a function of the column and the **positional** path, so the client derives a start token for any path it can name without a wildcard: `$.nested`, `$.a[2].b`. Labels are bound with a kind byte and as the final variable-length field, so `("ab", "c")` and `("a", "bc")` cannot collide.

Server side, the subtree under a start token is one recursive query. From `token-chain.sql`, which implements the derivations above (`chain.parent_tag(iv, t)` is `h16("p" ‖ iv ‖ t)` and `chain.mask(iv, t, c)` is `h16("w" ‖ iv ‖ t ‖ c)`) and runs as written on a stock PostgreSQL:

```sql
WITH RECURSIVE walk(depth, t, entry) AS (
    SELECT 0, t_start, NULL::jsonb
  UNION ALL
    SELECT w.depth + 1,
           chain.xor16(decode(e->>'w', 'hex'), chain.mask(decode(stored->>'iv', 'hex'), w.t, decode(e->>'c', 'hex'))),
           e
    FROM walk w
    JOIN LATERAL jsonb_array_elements(stored->'sv') e
      ON e->>'p' = encode(chain.parent_tag(decode(stored->>'iv', 'hex'), w.t), 'hex')
)
SELECT depth, entry FROM walk WHERE entry IS NOT NULL
```

Run against the fixture document with the token for `$.nested`, derived on the client from the labels alone, it returned the six entries under `$.nested` (`deep`, `list`, both elements, both `x` leaves) with their depths, nothing else; a garbage token returned zero rows; the root token returned all nine non-root entries; and the same document stored under a second IV shares no parent tag with the first. The mask for `w` includes the child's own ciphertext so that two siblings with the same `p` get different masks without the server needing to know anything about them.

**Why plain SHA-256 is enough here, and HMAC stays an option.** Three of the derivations hash a secret token with public bytes beside it, which is the shape that invites a length-extension question. It does not apply, for two independent reasons. Every output is truncated to 16 bytes (12 for the nonce), and a length extension needs the full 32-byte digest, because the digest is the chaining state the attacker resumes from; with half of it unknown the attacker is guessing 128 bits. And an extension can only produce the hash of a message that has the original as a prefix: each derivation starts with its own domain byte, so an extended `"p"` hash is never a `"w"`, `"g"` or `"t"` value, and within a domain the extended message names nothing that exists. For `t(child)` it is the token of a sibling whose label is `key ‖ SHA-256 padding ‖ x`, and the padding begins with a lone `0x80` byte, which is not valid UTF-8 and so is not a possible JSON object key. For the mask it is the mask of a sibling whose ciphertext is `c ‖ padding ‖ x`, and a real sibling's ciphertext is independent AES-GCM output. For `p` and `g` it is a tag no entry carries. Nothing in the system accepts one of these hashes as a proof of anything: the only authenticity check is the AES-GCM tag under the ZeroKMS data key. Keying the derivations with HMAC-SHA256 (`HMAC(t(parent), "t" ‖ 0x01 ‖ key)` and so on) would make "a token is a key" literally true and remove the need for this paragraph, at the cost of one extra compression per parent for `p` and one per matched child for the mask in the recursive walk, and a 64-byte XOR in plpgsql, since core PostgreSQL has no `hmac()`. Decision (2026-10-18): SHA-256 as written; HMAC is recorded as decision 7 below and is to be re-evaluated once Phase 3 has benchmark numbers over large documents and tables, not before.

What a token is: a capability for the **structure** of one subtree, in every row of the column, because the tokens are column-deterministic. It opens no value, which is under the ZeroKMS data key. It does expose the **key names** beneath it to guessing, as written: every child token below it is `H("t" ‖ t(parent) ‖ 0x01 ‖ key)`, a hash whose only secret is the parent's token, and the walk hands the server every descendant's token, so a server that holds a token can test a candidate name offline (`H("t" ‖ t(parent) ‖ 0x01 ‖ guess) = t(child)`) at every level of the subtree, in every row, for as long as the column lives. A selector does not allow this, because it is keyed with the index key. Key names are data whenever an object is used as a map, keyed by an email address, a user ID or a SKU. The remedy is to derive the label step under the index key, `t(child) = PRF(json/token ‖ column, t(parent) ‖ 0x01 ‖ key)[..16]` (and `0x02 ‖ LE64(index)` for an element): in this design the server never derives a child token from a label, it unwraps `w`, so keying the step costs the server nothing and the client one PRF per node in place of one hash. That is decision 11 below. Handing the server `t($.a)` in a query lets it see, for that query, which entries sit under `$.a` and how they nest. That is the same trust the client already extends when it sends a selector, and the server learns it only for the path asked.

The per-document salt (`iv`) in `p`, `g` and the mask means that **at rest**, with no token, the tags of two rows with identical shape are unrelated bytes. Nothing links shape across rows until a query supplies a token. This is the one place the proposal leaks strictly less than the alternative of a public parent pointer, and it costs nothing: the IV is already in `h`.

Wildcard paths. A client cannot derive `t($.a[*].b)`, because the token is positional. Extraction under a wildcard anchors at the nearest non-wildcard ancestor and gates on the selector: `subtree_at(doc, t($.a), s($.a[*].b))` walks from `$.a`, and emits an entry only once the walk has passed through an entry whose `s` matches. Scalar leaves under a wildcard need no token at all: `->` by selector returns them as today, and their nonce and AAD depend on `s` and `j`, not on `t`.

Arrays. `jsonb_array_length(doc, t)` is the count of children of `t`; `jsonb_array_elements(doc, t)` is the children, each a subtree root. Positional access (`$.a[2]`) is a token, not a selector, so the item (`[@]`) and positional (`[n]`) `ArrayIndexMode`s have no reason to exist in v4: wildcard only, and the chain for positions.

> **2026-10-24:** as written, a positional token names the element's children, not the element: a scalar at `$.a[2]` has no children and its selector is every sibling's, so `subtree(doc, t($.a[2]))` could neither return nor identify it (review of #1250). The implementation reaches a position from its parent: the client sends the parent's token and a position gate `#2:<selector>` (`JsonSubtreeKey::gates()`), `json_tree_subtree_at` admits the entry at ordinal 2 only if it carries the element selector, and returns that entry itself at depth 0 with its descendants below it. See the Phase 3b and 3c notes below (#1329).

> **2026-10-24 (design change, not yet built):** an object member's token drops its ordinal, every entry gains a self tag `x`, and the client expands wildcards itself, so it derives the token of any wildcard-free path and gates go away. See "Design change (2026-10-24)" at the end.

#### The sealed root: no root token, the document at the root (decided 2026-10-18)

Two properties make a token worse than a selector. It is a capability over structure rather than a presence bit, and it is deterministic per column, so a server that has seen it once can re-walk every row for as long as the column lives. The chain as written above hands the server the **root** token in two legitimate queries: a wildcard extraction anchored at the root (`$[*].x`) and `jsonb_array_elements` on a root array. `t($)` unlocks the shape of every document in the column, once, forever. Any shallow token is nearly as broad.

The fix moves the head of the chain down one level. With the option on:

- The root entry's `c` encrypts the **whole document**, as the v3 root entry does, not the root's label and kind. It carries no token-derived fields.
- The top-level fields are the chain **heads**: `t($.a) = PRF(json/token ‖ column, "$.a")[..16]`, derived from the path alone. A head carries no `p` and no `w`, since no parent token exists to link it to. Everything below a head is the chain as written.
- There is no `t($)`. No query can send it, because nothing is derived from it.

What a query can hand the server is then capped at one top-level field's subtree, in the rows it scans. A wildcard extraction anchored at the root, and the array functions on a root array, lose their server-side form and become a client-side decrypt of the root entry, which the client was going to fetch anyway. Whole-document decryption becomes one AEAD under the data key, with no walk and no index key, which is what cipherstash-client and the Go decrypt path do today. Everything else is unchanged: selectors, `vs`, group tags, the recheck, scalar `->`, and the walk for any path at depth 1 or below.

This is the depth-1 case of a general threshold `d` (tokens exist only at depth `≥ d`, every node above carries its subtree as ciphertext). `d = 1` is the only setting worth exposing. Its at-rest cost is small but not nil. The only subtree whose size it reveals is the document's, which the payload length reveals regardless; but the heads carry no `p` and no `w`, so a stored row shows which of its entries are top-level fields and how many there are, which the chain from the root hides once its parent tags are position-keyed. `d = 2` would reveal every top-level field's size at rest, in every row, correlated across rows by selector, which is more than the salted sibling tags it would replace, and it doubles the storage overhead. So the option is a **boolean**, not a depth: `false` is the chain from the root (`d = 0`), `true` is the sealed root (`d = 1`), on by default. The working name is "root node obfuscation"; the final name is decision 8. The option is part of `JsonOptions`, crosses the data-plan wire with the other index options, and is recorded in the header `h`, so a reader of a stored document knows which shape the root has without consulting the column's configuration.

Storage: one extra encrypted copy of the document's plaintext bytes, encoded on the wire like every other ciphertext. In hex characters, both sides counted alike, it is about 13% of the payload for a document of small scalars (around 15 bytes of plaintext per node, 30 characters, against about 230 characters of entry) and about 65% for one of long strings (200-byte leaves: about 410 characters of copy per leaf against an entry of about 630). Still strictly smaller than v3, which pays this copy at every level.

The same cap can also be imposed as a client policy on the chain-from-root wire: never send a token shallower than depth 1, and fetch the whole row for anything shallower. That costs no storage, but shallow extraction then transfers the whole document and whole-document decryption keeps the walk and the index key. The option above is the one proposed; the policy is recorded as the alternative.

#### Epochs: bounding a revealed token in time (recorded, not scheduled)

The sealed root caps how much a token unlocks. It does nothing about how long: a token is a function of the column and the path, so the server keeps it, and every row written later is as open to it as the rows it was used on. Per-row tokens would close that entirely and are not practical, because a client cannot derive a token for a row it has not read, so multi-row extraction would need a round trip per row. Epochs sit between the two. The head derivation takes an epoch: `t_e($.a) = PRF(json/token ‖ column ‖ e, "$.a")[..16]`, with `e` a small integer recorded in the header `h`, in the clear, beside the IV. Rows written under epoch `e` have heads nobody can derive without naming `e`, and a token revealed for epoch `e` unlocks rows of that epoch only. A query reaching several epochs carries one token per epoch it wants to reach, as a small map, and the walk picks the token by the row's own `e` (`tokens ->> (doc->'h'->>'e')`), which is one more lookup per row and no change to the recursion. Selectors and value selectors are **not** epoched, because containment and `->` have to match rows from every epoch with one needle; only the chain tokens are, and `p`, `w`, `g` and `n` follow them since they derive from a token. What this buys is a bound on the forward reach of a leak: a token the server saw in epoch 3 opens nothing written in epoch 4. What it does not buy is anything backward: rows of a closed epoch stay open to the tokens that were sent for them until they are re-encrypted, and the query cost grows with the number of live epochs, so the rotation cadence has to be set against the re-encryption cadence. The wire change is one small integer in `h` and in the derivation; the SQL change is one lookup. Neither is in the phased plan. The field should be reserved in the header from the first version so that adding epochs later is a new value rather than a new shape.

#### Position-keyed parent tags: siblings unlinkable at rest (for Phase 1)

`p = H("p" ‖ iv ‖ t(parent))` is the same value on every child of a node, so sibling groups are visible to anyone holding the row, with no token. That is the main at-rest residue of the chain. Keying the tag by the child's position removes it: `p_i = H("p" ‖ iv ‖ t(parent) ‖ i)`, with the child's ordinal `i` stored in the clear on the entry. At rest an observer learns only "this is some node's `i`-th child". The walk changes from one hash per walked node to `F` hashes per walked node, where `F` is one more than the largest `i` in the document (public), followed by the same equality join as now; `W × F` hashes for a walk of `W` nodes, which Phase 3 measures. Array children take `i` from their index, which the client needs for reconstruction anyway. Object children take `i` from a per-document shuffled order, derived from the document key, so the ordinal does not rank key names. The storage cost is one small integer per entry.

> **2026-10-22:** the parent tag is still position-keyed, but since Phase 3b the ordinal is not stored and there is no `F`: the ordinals under a node are dense from zero, so the walk probes them in turn and stops at the first miss, about `2N` probes for a subtree of `N` nodes.

### 3. Exact containment (#1231)

**The gap, verified.** `jsonb-semantics.sql` pins PostgreSQL's own answers, and `containment-oracle.sql` runs a plaintext-selector simulation of the v3 flattening (the PRF is injective in practice, so string selectors give the same containment answers as MAC'd ones) beside it:

| case | `jsonb @>` | v3 selector containment |
|---|---|---|
| `{"a":[{"x":1,"y":5},{"x":7,"y":2}]} @> {"a":[{"x":1,"y":2}]}` (the issue's example) | false | **true** |
| `{"a":[{"b":[{"x":1},{"y":2}]}]} @> {"a":[{"b":[{"x":1,"y":2}]}]}` (nested arrays) | false | **true** |
| `{"a":[{"b":{"c":1,"d":5}},{"b":{"c":3,"d":2}}]} @> {"a":[{"b":{"c":1,"d":2}}]}` (object inside element) | false | **true** |
| `{"a":[[1,2],[3,4]]} @> {"a":[[1,4]]}` (array inside element) | false | **true** |
| `["a"] @> "a"` (the issue's "plausible" false negative) | true | **false** |
| every other case tried (empty containers, duplicates, scalar vs array at depth, `{}` against an array, nulls, type confusion) | | agrees |

So the bug is exactly the issue's diagnosis: a needle array element that is a container with two or more constraints can be satisfied by different stored elements. Scalars in arrays are fine, single-constraint elements are fine. And the top-level scalar case is a real false negative today.

**The fix at rest.** Every entry under an array element carries `g`, the group tag of the nearest enclosing element; an element entry carries its own tag as `n` and its enclosing element's as `g`. Tags are `H("g" ‖ iv ‖ t(element))`: per document, random-looking, deterministic given the token.

**The fix in the needle.** The `Contains` query term serialises to `{sv: [...], grp: [...], alt?: {sv: [...]}}`:

- `sv` is the flat selector set, as today.
- `grp` is one group per needle array element that is a container: `{at: s(element path), need: [vs...], sub: [groups...]}`. `need` holds the value selectors inside the element down to, but not into, nested elements; `sub` holds the nested elements' groups. The element's own `vs` (its `MAP` or `ARRY` tag) is in `need`.
- `alt` is present only when the needle's root is a scalar: a second `sv` with the root value selector under `$[*]` instead of `$`, so a stored root array containing the scalar matches. `'"a"' @> '"a"'` matches through `sv`, `'["a"]' @> '"a"'` through `alt`.

**The fix in SQL.** Two stages, in one expression the planner handles well:

```sql
to_query(doc) @> q.sv                              -- GIN jsonb_path_ops, necessary condition
AND groups_ok(doc->'sv', q.grp, NULL)              -- recheck on the rows the index returned
OR (q.alt IS NOT NULL AND to_query(doc) @> q.alt)  -- a second GIN probe, bitmap OR
```

`to_query` projects each entry to `{s, vs}`; a needle element `{s: X}` or `{vs: Y}` is contained by any entry carrying it, so the existing GIN strategy carries over with both selectors on one entry. `groups_ok` is the recursive recheck: for each group, some element entry with `s = at` (and, below the top level, `g` equal to the enclosing group's chosen element) has every `need` selector on itself or on an entry whose `g` is its `n`, and satisfies its `sub` groups. It is plpgsql, it runs only on rows that passed the index, and it is a no-op for a needle with no container array elements, which is every needle the Rust `AtPath<Eq>` operator produces.

**Result.** `containment-oracle.sql` agrees with `jsonb @>` on 29 of its 31 cases, the six cross-element false positives included, and its closing query counts the disagreements (8 for the v3 form, 2 for the grouped form). The two it gets wrong are simulation artefacts, not design defects: the file canonicalises numbers as `numeric::text` so `2` and `2.0` differ (the real producer canonicalises by value, as cipherstash-client's `canonical_number` does), and the root-scalar case is fixed by `alt`, which the simulation does not implement.

**The preferred form: let native `jsonb @>` do the grouping (added 2026-10-18).** PostgreSQL's containment already has the rule `groups_ok` re-implements: a needle array element must be contained by *one* stored element, recursively. So project a stored document into a shape that nests by array element, and project the needle the same way:

```jsonc
{ "sv": [ {"s": "…"}, {"vs": "…"}, … ],            // selectors of every node outside any array element
  "el": [ { "sv": [ … ], "el": [ … ] }, … ] }       // one object per array element that is a container, recursively
```

Then `to_query(a) @> to_query(b)` is exact for arrays of containers with no plpgsql at all: the `sv` arrays check selector presence, and each needle `el` object has to fit inside one stored `el` object, which is the same-element rule. The GIN `jsonb_path_ops` index still serves it, because GIN is lossy for `@>` and the executor rechecks the real operator on the heap tuple; and the projection is computed once per row inside the expression index, so a query pays nothing for it. `alt` stays as it is. Two ways to obtain the grouping server-side, with identical leakage: build the projection from the `g` and `n` tags (a plpgsql `to_query`, immutable, run at index time), or store `sv` itself nested by element, which removes the tags from the wire and makes `->` by selector a `$.**` jsonpath lookup. Phase 2 tries the projection first, measures both, and keeps `groups_ok` only if neither engages the index. Whichever form wins, `n` and `g` are emitted only for elements that are **containers**: a scalar element carries one constraint, so grouping cannot be wrong for it, and the tags would reveal element membership for nothing.

> **2026-10-22:** the projection won, and it is stored rather than built: the client writes it beside `sv` as `q` (Phase 3), and since Phase 3b the entries carry no `n` or `g`. Element grouping is visible at rest through the nesting of `q` instead. The `grp` needle and `groups_ok` above were never built.

**`ContainedBy` (`<@`).** `col <@ needle` asks whether the stored document is contained by the query value, so the roles swap: the query term has to carry the whole projection of its own document, in the same element-nested shape a stored document projects to (so the same-element rule still holds), and the row's projection is the side tested for containment inside it. `jsonb_path_ops` indexes `@>`, `@?` and `@@`, not `<@`, so no GIN index serves this direction: it is a filter evaluated per row, as `<@` already is in v3, and a query that uses it at scale needs another predicate to bound the rows. The root-scalar `alt` does not carry over. It lets a scalar needle match a stored array, and for `<@` it is the stored side that would need it, which a stored document does not carry; so a stored root scalar is not found inside a needle root array, which is the one case where `<@` would disagree with `jsonb <@`. Either a stored root scalar gains the pair, or the case is documented as a known difference.

**Portability to v3.** The group tags and the recheck do not depend on the chain. If #1231 must also be fixed for rows cipherstash-client writes, the same `g`/`n` fields and the same `groups_ok` can be added to the v3 wire and SQL, with `g` derived from the document key instead of a token. This document does not propose that; it records that the fix is separable.

### 4. Wire format

A document in the new domain, `public.eql_v4_json_tree` (placeholder name; a sibling of `public.eql_v4_json`, not a replacement for any SteVec domain):

```jsonc
{
  "v": 4,
  "k": "sv",
  "i": { "t": "users", "c": "profile" },
  "h": "…",                       // key header, once: iv, key tag, descriptor, keyset id (SQL reads the iv and the flags at fixed offsets; see the note below)
  "sv": [
    { "s": "…", "vs": "…",                                  "c": "…" },            // $      sealed root: c is the whole document; no p, w
    { "s": "…", "vs": "…",                                  "c": "…", "op": "…" }, // $.hello = "world-1"   a chain head: no p, w
    { "s": "…", "vs": "…",                                  "c": "…" },            // $.list  (array)       a chain head
    { "s": "…", "vs": "…", "p": "…", "w": "…", "n": "…",    "c": "…" },            // $.list[*]  element 0 (object)
    { "s": "…", "vs": "…", "p": "…", "w": "…", "g": "…",    "c": "…", "op": "…" }  // $.list[*].x = 1, inside element 0
  ],
  "q": { "sv": [ {"s": "…", "vs": "…"}, … ], "el": [ { "sv": [ … ], "el": [ … ] } ] }  // the containment projection, written by the client (Phase 3)
}
```

> **2026-10-24:** `h` is not opaque to the SQL. The walk needs the document's `iv` to derive the parent tag `p`, and the sealed-root flag to know whether to fall back, and neither is stored anywhere else (review of #1250). The header's layout is frozen, so the implementation reads both from `h` at fixed byte offsets: `eql_v4_internal.json_tree_iv(h)` is the sixteen bytes at offset 22 and `json_tree_sealed_root(h)` is bit 0 of the flags byte at offset 1 (`packages/eql/src/v3/json_tree/functions.sql`, #1329). No field was added to the domain. The key tag and descriptor stay unread by SQL.

A `Contains` needle, `eql_v4.query_json`:

```jsonc
{
  "sv":  [ {"s": "…"}, {"vs": "…"}, … ],
  "grp": [ { "at": "…", "need": ["…", "…"], "sub": [] } ],   // only when an array element is a container
  "alt": { "sv": [ … ] }                                      // only when the needle root is a scalar
}
```

An `AtPath<Eq>` needle is `{"sv": [{"vs": "…"}]}`. An `AtPath<Gte>` term is the pair the ADR-0009 appendix already shows: a selector for `->` and a leaf ordering operand. A subtree request is `(t_start, s?)`.

With the sealed-root option off, the root entry's `c` is the root's label and kind only, and the top-level entries carry `p` and `w` like every other node. The header records which shape the document has.

> **2026-10-22:** as built, a stored document is `{"v", "i", "h", "sv": [{s, c, p?, op?}], "q"}`, with no `k`; a containment needle is a projection, `{"sv", "el", "alt"?}`, with no `grp`; and a subtree request is a token and one gate per step below it. The size estimates below predate both; the measured sizes are under Phase 3b.

> **2026-10-24 (design change, not yet built):** an entry becomes `{s, c, x, p?, op?}`, with the eight-byte self tag `x` on every entry, and a subtree request becomes a list of tokens with no gates. See "Design change (2026-10-24)" at the end.

**Size.** Per 16-byte field, hex costs 32 characters plus about six of framing. Measured against the envelope RFC's fixture document (`{"hello":"world-1","nested":{"deep":"constant"},"number":1}`, 5 nodes):

| | v3 today | proposed |
|---|---|---|
| entries | 10 | 5 |
| per leaf node | ~180 chars (path entry + value entry) | ~230 chars (`p`, `w` added; one entry) |
| per container node | ~40 chars + the whole subtree's ciphertext | ~190 chars, no subtree |
| this document | ~1,060 chars | ~1,140 chars |
| 100-element array of 5-leaf objects | ~5 KB document ciphertext at the root, repeated once more across the element entries, plus the leaves | leaves only |

On a flat five-node document the proposal is about 8% larger: the two chain fields cost more than the sentinel entry saved. The saving is the duplication, which grows with size and depth and is the term that dominates every real document. Encoding the 16-byte fields as base64url (22 characters) instead of hex (32) saves about 40 characters per entry and puts even the flat case ahead; `decode(x, 'base64')` is core SQL, so the choice is free. The phased plan should measure three shapes (flat, nested, array-heavy) before fixing the encoding.

### 5. Keys, nonces and AAD

- **One ZeroKMS data key per document**, requested under the column's descriptor, as today; the header `h` carries what `retrieve_keys` needs, once.
- **Nonce** `= H("nonce" ‖ s ‖ LE64(j))[..12]`, where `j` is the entry's ordinal. No two entries of a document share `j`, so the inputs are distinct, and two nonces collide only if the 96-bit truncation does: with probability about `N² / 2^97` for `N` entries, which is negligible but is not uniqueness by construction. Uniqueness by construction costs nothing more: the data key is fresh for every document, so `j` itself, as a 96-bit little-endian counter, is a nonce that cannot repeat under its key, and it meets the goal above where the hash only approximates it. Either way AES-256-GCM is safe without SIV. It is derivable for an extracted entry from public fields, so a wildcard-extracted leaf decrypts without a token. Reordering entries breaks decryption, which is tamper evidence, not a hazard: jsonb preserves array order.
- **AAD** `= PAE("stack-encrypt/json/entry/v1", keyset_id, descriptor, key_tag, s, j)`. A ciphertext moved to another entry, another document or another column fails to open.
- **PRF domains**, all PAE-framed and versioned as the existing terms are: `json/selector/v1`, `json/value/v1`, `json/token/v1`. The v3 `prefix` string is replaced by the column context, which the plan-builder document already decided.
- **Leaf ordering terms** derive as the `Ope` index derives them today, keyed by column, so the v4 scalar ordering query domains serve `AtPath<Gte>` unchanged. Binding them to the selector as well would stop two paths' leaves comparing against each other and is a one-line change; the phased plan should decide it, because it changes which query operand domain `AtPath<Gte>` takes.
- **Equal sibling values.** Two elements with the same value share `s` and `vs` (public, as today) but now have different ciphertexts, because `j` differs. The v3 residual case where equal siblings produce byte-identical ciphertexts is gone.

### 6. Leakage, side by side

| observer sees | v3 today | proposed |
|---|---|---|
| which paths a row has | yes, `s` | yes, `s` |
| which (path, value) pairs a row has | yes, value `s` | yes, `vs` |
| node count | yes (2N entries) | yes (N entries) |
| size of every subtree | yes, each path entry's ciphertext is its subtree | no, only leaf scalar lengths, as the v3 leaf entries already show |
| parent and child relation | inferable from subtree sizes and cross-row co-occurrence | hidden at rest; sibling grouping (`p`) and element grouping (`g`) visible at rest as per-document random tags; linkable only with a token the query supplies |
| shape equality across rows | selectors are column-deterministic, so yes | tags are salted by the document IV, so no, until a token is supplied |
| which leaves sit in the same array element | yes, whenever elements are indexed: document order plus the per-element `a` flag, or position selectors outright (corrected 2026-10-25; this row first said no) | yes, `g`. Required for exact containment, and bounded to array elements |
| equal values at two paths | hidden | hidden |
| equal values in sibling elements | ciphertexts equal (selectors already equal) | ciphertexts differ |
| key names | hashed into `s` | hashed into `s`; also encrypted in `c`; under a token the query supplied, testable by guessing until the label step is keyed (decision 11) |
| at query time, a subtree extraction | reveals the selector asked | reveals the selector or token asked; a token also reveals that subtree's shape for the rows scanned, for as long as the column lives, since tokens are column-deterministic, and, as written, lets the server test guesses of the key names beneath it (decision 11) |
| the broadest token a legitimate query can send | none exist | with the sealed root: one top-level field's subtree. Without it: `t($)`, the whole column's shape |
| how long a revealed token stays useful | not applicable | for as long as the column lives; epochs (recorded above, not scheduled) would bound it to rows written under the epoch it was issued for |

> **2026-10-22:** parent tags are position-keyed (Phase 1), so siblings do not share a `p` at rest. Since Phase 3b there is no `g`: which leaves sit in the same array element is visible at rest through the nesting of the stored projection `q` instead.

> **2026-10-23 (review of #1336):** the "proposed" column of the shape-equality and parent-and-child rows is wrong for the format as built, and was wrong for the design as written. Neither the tags nor their salt are what decides it: the entries of `sv` (and the pairs of `q`) are stored in depth-first pre-order, an object's members in sorted key order, under selectors that are the same in every row. A row's sequence of selectors therefore fixes its shape exactly, the parent of every node is inferable by comparing rows (and is exact for the top-level fields under the sealed root, whose entries are the ones with no `p`), every array's length is the count of its element selector, and the relative order of sibling key names is visible across rows. `packages/eql/docs/reference/json-tree-leakage.md` states the format as built; the decision this leaves open is recorded under Phase 4.

> **2026-10-24 (design change, not yet built):** the "subtree extraction" and "broadest token" rows change: a read sends the tokens of exactly the nodes asked for, never a top-level field's or an array's unless that is what is read. See "Design change (2026-10-24)" at the end.

### 7. Performance

- **Encrypt:** per node two PRFs (`s`, `vs`), three hashes (`t`, `p`, mask), one small AEAD. v3 does two MACs and one AEAD over the subtree bytes. Fewer bytes encrypted at every depth above the leaves.
- **Containment:** the GIN probe is unchanged in cost (two keys per entry instead of two entries with one key). The recheck runs per returned row, in plpgsql, only for needles with container array elements, and scans `sv` once per group.
- **Scalar `->`:** one entry, as today.
- **Subtree `->`:** a recursive CTE, one `jsonb_array_elements` scan of `sv` per depth level. Linear in document size times depth of the subtree. Adequate for documents of hundreds of entries; `bench-eql` should measure a 1,000-entry document before this is called settled.
- **Decrypt a document:** with the sealed root, one AEAD on the root entry, as today. Without it, the client walks the chain locally: N hashes plus N small AEADs; the client has the index key, so no extra round trip either way.
- **Encrypt, with the sealed root:** one more AEAD, over the whole document, beside the N small ones.

> **2026-10-22:** as built, encrypt is two PRFs per node (`s`, `vs`) and up to three hashes (`t`, `p`, and an object member's rank), with no mask. The walk reads the document once into a map keyed by parent tag (Phase 3) and probes it, about `2N` probes and `3N` hashes for a subtree of `N` nodes (Phase 3b); measurements are under Phase 3 and Phase 3b.

### 8. Standard PostgreSQL

Everything the server does: `sha256(bytea)` (core since PostgreSQL 11), `get_byte` / `set_byte` for a 16-byte XOR in plpgsql, `decode` / `encode`, `WITH RECURSIVE`, `jsonb_array_elements WITH ORDINALITY`, and `jsonb_path_ops` GIN. No pgcrypto, no superuser, no C. The same posture as the v3 surface Supabase runs today.

> **2026-10-22:** with no XOR since Phase 3b, the walk needs no `get_byte` / `set_byte`: it is `sha256`, `decode` / `encode`, a jsonb object lookup and `WITH RECURSIVE`.

## Further mechanisms (added 2026-10-18)

The four above are in the phased plan: the native-`@>` projection and container-only tags under containment, the sealed root and position-keyed parent tags under the token chain. Four more are recorded here, with what each buys and costs, so that none is rediscovered as free.

**A per-path index policy, and opaque subtrees (for the phased plan, as a wire form).** v3 emits `s`, `vs` and `op` on every node. `vs` on a low-cardinality field such as `$.country` is a frequency histogram of that field across the table, in the clear; `op` on every number is an order oracle nobody asked for. The column should declare, per path or path prefix, which nodes get equality (`vs`), which get ordering (`op`), which arrays get grouping tags, and which subtrees are **opaque**: sealed as one blob at their parent, with no entries beneath, invisible to containment and extraction below that point. Opaque subtrees are also the answer to a 10,000-node document at about 230 characters per entry. Runtime cost is nil; the cost is a wire form for the policy on the data plan, which the match index's options already needed (plan-builder Additions, item 7). The phased plan should define the wire form and implement `vs` and `op` gating and opaque subtrees; the default stays "everything indexed", which is v3's behaviour.

**Length padding (recorded).** Pad each leaf plaintext to a bucket before sealing, the next 16 bytes or power-of-two buckets above a threshold, to blunt string-length fingerprinting. Cheap, and a per-column option. Padding the entry *count* with dummy entries, random `s`, `vs`, `p`, `w` and `c` that no selector or token ever matches, hides node counts and array lengths at about 230 characters per dummy; an option for small, sensitive documents only.

**ORE leaf terms beside OPE (recorded).** An OPE query bound reveals roughly where the bound sits in the order; an ORE query term is the left ciphertext only and reveals nothing beyond the comparison results. The phased plan keeps OPE leaves; the leakage argument for ORE leaves is the query-time one ADR-0002 already makes for scalar columns, and the leaf term is the same `Ore` index the engine has.

**Salted selectors for at-rest frequency hiding (recorded, with its cost).** `vs' = H(vs ‖ iv)` makes value selectors unlinkable across rows at rest, so no histogram exists until a query is made. The server then has to hash each needle selector against each row, which forfeits GIN entirely and makes every containment query a sequential scan. Defensible only for a small, rarely queried, highly sensitive column.

**Measure bytes on disk, not characters (for Phase 3).** jsonb is TOAST-compressed. Hex at four bits per character compresses better than base64url at six, so the character-count argument for base64url may not survive compression; and 12-byte selectors are collision-safe for any realistic column (birthday bound around 2^48 distinct values). Phase 3 compares hex and base64url, 12 and 16 bytes, under pglz and lz4 before the encoding is fixed.

## The phased plan

Scope: prove the three changes end to end with real encryption under the fake key source against a real PostgreSQL, measure size and query cost, and leave the wire fields decided. Not in scope: Go, TypeScript, bindings regeneration, the build-tool integration, case folding, ORE leaf terms, lock context.

**Phase 0, the oracle, no crypto.** Port `containment-oracle.sql` into the SQLx suite as a DB test that drives the **real** `eql_v3` functions with plaintext string selectors (the v3 domain CHECKs accept any string for `s`, `c` and `h`), and reports every disagreement with `jsonb @>` over a corpus of documents and needles. This is #1231's step 1, it pins the six false positives and the false negative against the shipped SQL, and it runs on a fork PR. Acceptance: the test fails on v3 for exactly the cases this document lists, and nothing else.

**Phase 1, the index in Rust.** `Json: Index<Value>` with the flattening, selectors, tokens, tags, nonces and AAD above, behind a `json` feature; the `JsonDocument` round trip; `JsonQuery` with `grp` and `alt`; `JsonSelector` and `JsonSubtreeKey`. Tests under `FakeDataKeySource`: round trip of nested documents and arrays; every entry's nonce distinct; unwrap of every child from its parent's token and of nothing from a wrong token; an entry moved, reordered or regrafted fails to open; the needle generator's `grp` against a hand-written expected shape for the issue's example; the selector for a path equal to the `s` of the stored entry; a property test that a document's entries decrypt and reassemble to the input for arbitrary `serde_json::Value`s. ## Implementation notes (2026-10-19, Phases 1 and 2)

The index, the SQL and the live oracle landed in the pull request stacked on this document; what follows records where the code is and where it departs from the design above, so the two can be read against each other. Phase 0 was folded into Phase 2, and Phases 3 and 4 remain open.

**Where it is.** The engine half is `packages/stack-encrypt/src/json/`: `Json` is the index (`Index<serde_json::Value>`, term `JsonTerms`), `target::json_document` the sealing operation, `JsonDocument` the stored term and an `EncryptFrom<Value>` / `DecryptInto<Value>` target, `JsonQuery` the needle for `Contains`, `ContainedBy` and `AtPath<Eq>`, `JsonLeafQuery` the operand for the orderings at a path, and `JsonSelector` / `JsonSubtreeKey` the extraction keys, derived through `KeysetCipher::json_selector` and `json_subtree_key`. `IndexSpec::Json(JsonOptions)` is the data form, with the key `"json"` and `{"json": {"sealed_root": …}}` as its wire form; a data plan refuses it as an output (`Reason::JsonIndexPending`) and reaches it through the `JsonSearch` target, whose options are the index's (`TargetOptions::Json`), on a field of the `json` kind. The SQL is `packages/eql/src/v3/json_tree/`, confined to EQL v4, where its domains take the names EQL v3 gives its searchable JSON document (decided 2026-10-25, replacing the placeholder `eql_v4_json_tree` names above): `public.eql_v4_json_search`, `public.eql_v4_json_entry`, `eql_v4.query_json` and `eql_v4.query_json_leaf`, with the target `JsonSearch`, while the v3 SteVec SQL is confined to EQL v3; the EQL types are `packages/eql/crates/eql-bindings/src/v4/json_tree.rs`; the oracle is `packages/eql/tests/encryption/tests/json_tree.rs`, which stores the design's corpus, and batches of documents proptest generates (`json_tree/generated.rs`), encrypted beside their plaintexts and checks that `@>` and `<@` over the encrypted column select the rows PostgreSQL's own `jsonb` operators select over the plaintext column, on the GIN index and on a sequential scan, each plan shown in `EXPLAIN`. The pure-Rust half of that oracle is `packages/stack-encrypt/tests/json_index.rs` (`given_the_design_corpus` and the proptest properties in `given_generated_documents`), against a model of `jsonb @>` pinned to the answers in `jsonb-semantics.sql`.

**Decisions taken by the code.** Of the eleven listed below: 1, hex for every sixteen-byte field and base64 for `c` and `h`, pending Phase 3 (taken on 2026-10-23, Phase 3d: base64 for every field the SQL reads, base85 for `c`); 2, leaf ordering terms bound to the column only, numbers as the `f64` they round to and strings as text, under the scalar `Ope` index's derivation; 3, wildcard arrays only; 4, group tags on, and only on container array elements; 5, the child count is in every container node's ciphertext, and a truncated subtree is `OpenedType`, not a shorter array; 7, plain SHA-256; 8, the option is the boolean `sealed_root`, on by default, recorded in the header's flags; 9, the projection is built from the tags server-side (`eql_v4.json_tree_query`) and `groups_ok` was not needed; 10, position-keyed parent tags on, the ordinal stored as `o`, object members ranked under the parent's token; 11, keyed: in this first form a child's token was `PRF(json/token-step ‖ column, PAE(t(parent), 0x01, key))` (`0x02, LE64(index)` for an element) and an object member's rank `PRF(json/rank ‖ column, PAE(t(parent), key))`, each under its own PAE domain, so a token's holder could neither test key names against the child tokens the walk unwraps nor rank guessed names against the ordinals. Decision 6 is out of scope, as proposed. (Both steps were first hashed unkeyed, as the token chain section above writes them, and were corrected before any release.)

> **2026-10-22:** 4 and 10 have since moved. The grouping lives only in the stored projection `q`, with no `n` or `g` on an entry (Phase 3 and 3b). Parent tags are still position-keyed and an object member's ordinal is still its rank under the parent's token, keyed (decision 11), but the ordinal is no longer stored (Phase 3b). The ordinal chain of Phase 3b derives a child's token from its ordinal, which carries no label, so the keyed label step of decision 11 is gone with it and only the keyed rank remains.

**Deviations.**

- *Nonces are random, not derived from the selector and ordinal.* Every entry seals through the engine's one AEAD path (`vitaminc-encrypt`'s AES-256-GCM with its own random 96-bit nonce, carried in `c`), so there is one leaf cipher in the crate and no second AES-GCM call site. Uniqueness under one document key is then probabilistic (`N² / 2^97` at `N` entries) rather than structural. The entry's AAD still binds its ordinal `j`, so a moved or reordered entry fails to open as the design requires; the cost is twelve bytes per entry, which Phase 3 should count.
- *The ordinal is `o`, not `i`*, because `i` is the envelope's identifier, which `->` grafts onto an extracted entry. An extracted entry also carries `j`, its ordinal in the document, which its AAD is bound to, and a walk adds `d`, its depth below the start. (2026-10-22: since Phase 3b `o` is not stored at all.)
- *The subtree walk returns a node's descendants and not the node itself.* The walk addresses nodes by their parent, and the design's wire has no field that names a node by its own token. The client reads the node's kind from its children's labels; a node with no descendants, an empty container or a scalar, yields no rows, and `->` on its selector returns the node. A self tag per node would close this at sixteen bytes an entry and is left to Phase 4. (2026-10-22: a gated walk, `json_tree_subtree_at`, now returns the node its gates reach at `d = 0`, with no self tag; the ungated `json_tree_subtree` still returns descendants only.) (2026-10-24: an eight-byte self tag on every entry is now the design; see "Design change (2026-10-24)" at the end.)
- *Containment is not `STRICT` in SQL.* PostgreSQL inlines a `STRICT` SQL function only when it can prove the body is NULL for a NULL argument, and the `OR` that adds the needle's `alt` probe is not provably NULL; un-inlined, the call was an opaque filter and the GIN index never engaged. `eql_v4.json_tree_contains` and the `@>` / `<@` wrappers over it are declared without `STRICT` and return NULL for a NULL side on their own.
- *`<@` cannot match a stored root scalar inside a needle root array*, since a stored document carries no `alt` pair. The oracle records the case; `@>` is exact.
- *Value selectors compare strings byte for byte*, with no Unicode normalization, because `jsonb @>` does, and the oracle is agreement with `jsonb @>`. The scalar equality index normalizes to NFC; a JSON value does not. Numbers canonicalize by value, so `2` and `2.0` are one value, as `jsonb` compares them.
- *`AtPath<Eq>` is the containment of the needle document that holds the value at the path*, with a position in the path read as the wildcard, rather than a single `{vs}` entry: a leaf inside an array element sits in that element's group of the projection, and the needle has to say which group. Containment of that needle is equality only for a scalar, so a container value is refused (`TermError::JsonValueNotScalar`; `op::Contains` asks the containment question), and the needle carries no `alt`, so `("$", 1)` does not match a stored `[1]`.
- *The data-plan form and the catalog are not done.* The Go guest, `stashgen`, the target table and `v4::all()` do not know the family; `IndexSpec::Json` crosses the wire and is refused with a reason. The family is hand-written in `eql-bindings` as the SteVec structs are. Both are the next bindings issue.
- *A document is at most 127 levels deep*, under either root option. The sealed root's plaintext is the document as JSON, and `serde_json` parses JSON back only to 128 levels of nesting, so the 512 levels the walk first admitted sealed documents that then never opened. The bound is the reader's, so a document too deep fails when it is sealed, while the caller still holds it, and not when it is read.
- *A stored document is read as untrusted input.* Its chain fields are not authenticated, and whoever holds a token can write tags that form a cycle or a chain deeper than any sealed document. `JsonDocument::children` checks each entry at its own ordinal instead of looping over a fan-out the document chooses; `JsonDocument::subtree` and the SQL walks stop below 127 levels, and the Rust walk also stops once it has returned as many entries as the document holds; the rebuild of a subtree's rows refuses a repeated row and a nesting deeper than 127 levels as `OpenedType`. Each would otherwise have overflowed the stack, looped, or allocated what the document asked for. (Phase 3b replaced `children` with a probe from ordinal 0 to the first miss, bounded by the entry count, and derives a child's token from its ordinal by hash, so no stored chain can form a cycle and the SQL walks need no depth bound; the Rust walk keeps both of its bounds and the rebuild keeps its own.)
- *Nothing wipes the plaintext copies the walk makes* (the per-node scalars it clones before sealing), where the scalar paths hold theirs in `Zeroizing`. A `serde_json::Value` does not zeroize; a follow-up should walk the caller's value without copying scalars out of it. (2026-10-23: done. The JSON plaintext is held under vitaminc's `Protected` as the scalar paths hold theirs. The walk no longer copies a scalar or a key out of the caller's value: it encodes each node's plaintext straight into a `Protected<Vec<u8>>`, sized before it is written so it never reallocates, and hands that to the cipher, which takes a `Protected` anyway; the sealed root's JSON is measured first and written once into its own. On the way back, the bytes the cipher opens stay in its `Protected<Vec<u8>>` while they are parsed, and every key, scalar and sealed-root document read out of them is wrapped as it is made (`zip_ref` over the bytes), in `Protected<PlainJson>` for a value: `PlainJson` is a newtype over `serde_json::Value` whose `Zeroize` wipes every string, values and object keys alike, and overwrites numbers and booleans in place. A subtree is rebuilt inside a `Protected`, each member moved in from its own, and a value leaves the wrapper only where it is handed to the caller. The sealed-root fallback selects the walked path inside the document's `Protected`, so the whole document is wiped when the selection is made and only the selected nodes come out. What remains: numbers and booleans have no volatile overwrite without unsafe code, which this crate denies, so theirs is best-effort; and outside the decrypted plaintext, the query and term side still holds plaintext in places vitaminc does not reach from here: an accessor's needle document (`JsonPath::needle`), the canonical bytes of a value selector inside vitaminc's PAE `Context`, and the key names in each term node's positional path.)

## Implementation notes (2026-10-21, Phase 3: first measurements and the fixes they forced)

The family was measured at 10,000 rows in the `cipherstash/benches` repository (branch `feat/json-tree-benches`, report `report/JSON_TREE_COMPARISON.md`; the first run at commit 076ebfc, the re-measurement of this phase's fixes at 57abcf9, both at 10,000 and 100,000 rows) against the v3 SteVec and native `jsonb`, on a flat five-node corpus and a nested corpus of about 220 nodes per document. The figures below are that report's at 10,000 rows unless they say otherwise. The flat corpus was on par with v3 (containment 0.47 ms against 0.23 ms, equality at a path 0.70 against 0.81 ms, the containment index eleven times smaller). The nested corpus was not: containment 70 to 80 ms per query, a 244-entry subtree 10 s, the GIN index 44 s to build. Three mechanisms accounted for it, and the fixes landed in the pull request stacked on the family's:

- **The projection is stored, not rebuilt.** Decision 9 above chose to build the element-nested projection server-side from the tags (`eql_v4_internal.json_tree_group`, recursive plpgsql). That function ran once per candidate row in the lossy GIN recheck, and again in the Filter, at about 3 ms per 220-entry document: the whole cost of containment on the nested corpus, and of the index build. The client already derives the shape for the needle, so the document now writes it to the wire as `q` beside `sv`, the domain CHECK validates it as a group, and `eql_v4.json_tree_query(doc)` is `doc -> 'q'`. It returns `jsonb` rather than `eql_v4.query_json_tree`, because a domain cast runs the needle's recursive CHECK, and the recheck would pay it per row. And it is plpgsql with `COST 1000`, not an inlinable SQL function, for a reason the first re-measurement found: inlined to `value -> 'q'` the filter is costed as one operator, and the nested table's rows are TOASTed, so its main heap is a few hundred pages and a sequential scan over it was costed below the GIN bitmap scan and chosen, at 1.5 s for a one-row match on 10,000 rows (17 s on 100,000), because every row is decompressed to read `q`. Un-inlined, the call keeps its cost, the index expression `eql_v4.json_tree_query(col)` still matches it, and the planner takes the index: 0.5 to 0.7 ms for a one-row match, 3.2 ms for ten deep-object rows (0.36 ms native), and 5 s to build the index. Nothing new is revealed: `q` is the selectors already in `sv`, grouped as `sv`'s own `n` and `g` tags already group them. It is not small: 19,100 of a nested document's 114,309 characters, about 17 per cent, though nothing measurable on disk, since its hex pairs compress against `sv`. And it is trusted as written: the CHECK validates its shape, not that it is `sv`'s, so a row written by anything but this index can answer `@>` differently from `->`, the walks and decryption, which answer from `sv`. The server-built projection could not disagree with the entries; verifying `q` against `sv` at write time would restore that at roughly the old per-row cost, paid once per write instead of once per recheck, and is left open. The deviation this replaces, "9, the projection is built from the tags server-side", is withdrawn; the `groups_ok` fallback remains unneeded.
- **The walk reads the document once, keyed by parent tag.** The shipped walk put `json_tree_parent_tag(iv, t, o)` inside a LATERAL scan of `sv`, so it was evaluated once per (node, ordinal, entry): about 670,000 SHA-256 evaluations for the 244-entry subtree. The walk now builds one jsonb object of the chained entries keyed by `p` (`eql_v4_internal.json_tree_by_parent`) and looks each computed tag up in it, so a level costs its fan-out in hashes plus one lookup each, which is the design's `W × F` as written. The `$.orders` subtree walks out in 23 ms (the six-entry `$.company` subtree in 2.8 ms); `children` and `child_count` in 1.6 ms, from 7.1. The report's prose calls `$.orders` the same 244 entries as the first run's 10.2 s, while its table counts 122 rows for the walked scenario; which count the 23 ms is for is still to be confirmed. The walk is bounded by the document as well as by depth: the fan-out it probes is at most the document's entry count, where a stored `o` could otherwise ask for two billion, and it returns at most as many rows as the document has entries, where a stored `w` that wraps a child's token to its parent's could otherwise double the rows at every level. Neither changes a sealed document's walk; the Postgres suite held both against hostile documents (`postgres_walks_end_on_hostile_documents`). The ordinal chain of Phase 3b removes both cases rather than bounding them: a child's token is a hash of its parent's, so a chain cannot loop back, and the walk probes ordinals until the first miss rather than up to a stored fan-out. Its walk carries no depth bound either, so the same test now holds it to one row per entry on a chain of 300, deeper than any sealed document.
- **A walk has a budget and falls back to the sealed root.** With the root sealed, the root's ciphertext is the whole document at about 1.3 times the plaintext, where a walk returns about 440 characters per entry and pays the fan-out in hashes per node visited. Past a dozen or so entries the document is cheaper on both sides, so `json_tree_subtree` and `json_tree_subtree_at` take a `budget` (default 64) and, once the walk passes it, return the root entry alone with `d = 0`. The client opens the root to the whole document and takes the walked path over it, over the new `JsonPath::select`, and the result is what the walked rows open to: the path is attached with `JsonSubtree::below(path)` for `json_tree_subtree`, whose rows are the descendants of the path's node, and `JsonSubtree::at(path)` for `json_tree_subtree_at`, whose rows are the nodes the path reaches (the same two on `JsonTreeSubtree` in the bindings). The two differ when the rows are opened as a list, to the node's children or to the node, which is why the rows cannot be opened without saying which walk they came from. (2026-10-23, the owner's option (c) from the #1325 review: the caller no longer says it. The path rides on the key it was derived from, `JsonSubtreeKey::path`, and the key builds the rows' wrapper, `key.open(rows)` in stack-encrypt and `JsonTreeSubtree::from_key(&key, rows)` in the bindings; a key with no gates keyed `json_tree_subtree` and opens below the path's node, a key with gates keyed `json_tree_subtree_at` and opens at the nodes the path reaches. There is no path-less constructor and no `below` or `at` to attach, so rows that cannot open past the budget cannot be built, and a caller unaware of the budget is not caught out by a document that grows past it.) A budget of 0 never falls back, a token that names no node yields no row under any budget, and an unsealed root is always walked out. `$.orders` returns the root in 9.5 ms, against 23 ms walked out; `json_tree_subtree_at` over its items in 13 ms against 23. Two costs are not in those numbers: the client's, since the benchmarks do not decrypt, which for the fallback is one AES-GCM open and a JSON parse of a document about 1.3 times the plaintext's size; and the plaintext the client then holds, which is every field of the document and not the subtree asked for. The data key is the same, so nothing is readable that was not, but the note above that a `serde_json::Value` is never zeroized now covers the whole document on every subtree read past the budget. (2026-10-23: no longer; the fallback's document is held under `Protected` and wiped once the walked path is selected from it, and only the selected nodes reach the caller. See the Phases 1 and 2 note on plaintext copies.) This is the sealed root paying for itself a second time: it is also what makes the fallback possible.
- **`json_tree_path_query_first` is costed at 1000.** `(col -> sel) > $1` extracts through it, and under a prepared statement's generic plan (what every driver reaches after five executions) the default cost chose a sequential scan with the extraction as a Filter over the functional btree: 16.9 ms against 0.11 ms with the index, at both tiers.

Still open from the measurements, filed as a follow-up: `->` scans `sv` on every extraction (0.6 ms on a nested document, 0.2 on a flat one, against 0.1 native; an index of `sv` by `s` would make it a lookup); `json_tree_contains` plans a second GIN probe for `alt` even when the needle carries none; `ORDER BY ord_term(col -> sel)` measured 0.96 ms against v3's 0.25 ms on an index scan both ways, unexplained; and the nested document is 29 times its plaintext in characters and 34 times on disk (hex tags, a random nonce per entry, the sealed-root copy, and now `q`), which decisions 1 and 6 above and the opaque-subtree policy are the levers on. Also open, for the owner: whether the budget should be on by default (a caller who opens a walk's rows without attaching a path works until a document passes the budget, then fails), and whether to verify `q` at write time.

## Implementation notes (2026-10-22, Phase 3b: the ordinal-chained walk)

A review of the stored form after the Phase 3 measurements found three fields nothing read and two the walk did not need, and replaced the chain step. The wire is now `{"v", "i", "h", "sv": [{s, c, p?, op?}], "q"}`.

- **`vs`, `n` and `g` are gone from the entries.** Once `q` was stored (Phase 3), no SQL function read an entry's value selector or group tags: containment reads `q` alone, and the engine read them only to rebuild `q` on deserialize. The engine now takes the stored `q` as the projection. That is no change in trust: `q` and the entry fields were equally unauthenticated (only `c` is, through its AAD), and a tampered `q` changes which rows a containment query returns and nothing else. On the nested benchmark document (213 entries on average) the values of those three fields were 15% of `sv`.
- **Tokens chain by ordinal.** `t(child) = H("t" ‖ t(parent) ‖ LE32(o))` replaces the label-derived step. The server derives every hit's token from its parent's as it walks, so `w` (the wrapped token) is not stored. The cost is that the client cannot derive an object member's token, because an ordinal is a rank among sibling keys it does not know. It derives a chain head's token and those of the array positions that directly follow the head, and sends one gate per further step (`JsonSubtreeKey::gates()`: the step's selector, or `#n` for a position); `json_tree_subtree_at(doc, token, gates, budget)` descends through them, and `json_tree_children` and `json_tree_child_count` take the same gates. A wildcard step's selector is every element's, which is the old `subtree_at` gate generalised to every depth. (2026-10-24: to be reversed for object members, whose tokens drop the ordinal, and with them the gates; see "Design change (2026-10-24)" at the end.)
- **The walk probes to the first miss.** The ordinals under a node are dense from zero (positions for arrays, a permutation for objects), so the walk tries `0, 1, 2, …` and stops at the first miss. `o` is not stored and `json_tree_fanout` is gone. A subtree of `N` nodes costs about `2N` probes (`N` hits, and a miss for every node visited), each a SHA-256 and a map lookup, plus a SHA-256 per hit for its token, where it cost `F` probes per visited node, `F` being the widest node in the whole document; on the nested corpus a wide `items` array taxed every object walk in the same document.
- **Depth is reported from the reached node.** A gated walk returns the node its gates reach with `d = 0` and its descendants beneath it, so the client can tell "the value at the path" (one reached node) from "the children of a node" (no `d = 0` row) without the path. A wildcard reaches several nodes and opens as a list. The ungated `json_tree_subtree(doc, token)` is now `json_tree_subtree_at` with no gates, and returns the token's node's descendants from `d = 1` as before.
- **Leakage.** At rest, the same as Phase 3 less what the stored ordinals told: their multiset gave, for every `k`, how many nodes in the chain have more than `k` children. `p` is still salted by the document `iv`. Under a token, the same: a token still unlocks the shape of that subtree in every row. The `w` mask's binding to `c` (a swapped ciphertext broke the walk on the server) is gone; the swap still fails when the client opens the entry, because `c` is bound to `s` and `j` in its AAD.
- **The chain step binds the child's selector (2026-10-23, review of #1329).** As first built, `t(child) = H("t" ‖ t(parent) ‖ LE32(o))` dropped the kind byte the label-derived step had (`0x01` for a key, `0x02` for an index), and an ordinal does not say which kind of child it numbers: an array element's is its position, an object member's its rank. Rows of one column need not agree on a node's kind, so the token the client derives for `$.a[0]` was, in a row whose `$.a` is an object, the token of the member ranked first, and a walk from it returned that member's subtree as the element's; a `#n` gate admitted the same member. `jsonb` has no node there (`jsonb_path_query_first(doc, 'strict $.a[0]')` is NULL), and the sealed-root fallback, which selects over the plaintext, agreed with `jsonb`, so one row answered differently under and over the budget. The step is now `t(child) = H("t" ‖ t(parent) ‖ s(child) ‖ LE32(o))`, the child's own selector bound in. The server holds every hit's `s`, so it derives the token as before (`eql_v4_internal.json_tree_child_token(token, s, o)`), and the client knows an element's selector from the path (the wildcard's), so it still derives positional tokens after a head. An element's selector is the wildcard path's and a member's names its key, so they never share a token. A position gate carries the element selector too, `#n:<selector>`, and the walk admits the hit at ordinal `n` only if it carries it. Nothing about leakage moves: the selector is stored beside the entry, and a token's holder already learns it with every hit. `postgres_a_position_reaches_array_elements_only` holds both forms against `jsonb`'s strict path over the plaintexts.

## Implementation notes (2026-10-22, Phase 3c: the ordering term is opt-in per path)

After the Phase 3b measurement the largest field in a stored document was `op`, the CLLW OPE term on every number and string leaf: 24,832 of the nested document's 85,157 characters, about 80 bytes of hex a leaf, on 156 leaves of which the benchmark's queries order two. An ordering term is also the one field that reveals something across rows at rest (the order of the leaf's value among every row that holds one), on fields nobody asked to order. "Further mechanisms" above proposed a per-path index policy with "everything indexed" as the default; the `op` half of it is now built, and the default is reversed: **no path is ordered unless the index says so.**

- **`JsonOptions` gains `ordered`**, a set of `JsonPath`s, beside `sealed_root`. The walk derives a leaf's `op` only when some ordered path covers the node's positional path (`JsonPath::covers`): a key step matches the same key, a wildcard step covers any array position and the wildcard, a position covers that position alone. So `$.orders[*].total` orders the total of every order and `$.scores[0]` the first score only; literal positions and wildcards are both allowed. The set is part of the index's identity like `sealed_root`, and crosses the data-plan wire as `{"json": {"sealed_root": true, "ordered": ["$.age", "$.orders[*].total"]}}`, paths as text, written in canonical order. It is not recorded in the header: a stored leaf shows whether it carries a term.
- **An ordering query at a path the index does not order is refused** (`TermError::JsonPathNotOrdered`) when the query is awaited, before any keyset loads. Without the refusal, `ord_term` returns NULL for every stored leaf at the path and the comparison silently matches no row. A wildcard query path is covered by a wildcard only, since a position orders elements the wildcard would compare against.
- **A position in an ordered path is refused (2026-10-23, review of #1329).** As first built, `$.scores[2]` ordered the third score alone, and an ordering query at `$.scores[2]` under an index ordering `$.scores[*]` was accepted. Neither works: an ordering compares the leaf `->` extracts by the path's selector, and a selector reads every position as the wildcard, so `->` returns the first element at the path. A query at an ordered `$.scores[2]` compared the first score, which carries no term, and matched no row, which is the failure the refusal above exists to prevent; a query at `$.scores[2]` under `$.scores[*]` compared the first score and returned rows for the wrong element. `JsonOptions::ordering`, the data plan's `ordered` and an ordering query now refuse a path that names a position (`TermError::JsonOrderingAtPosition`), and sealing under options whose `ordered` field holds one, which only direct construction can produce, is refused the same way. Ordering at an array element by position would need an extractor that reaches a position, which `->` by selector is not; it is not scheduled.
- **A plan can be laid out by a value.** The typed plan had no place for options: `encrypt_into::<JsonDocument>()` reads the type's own `EncryptFrom`, which is static, so every typed plan sealed under the defaults and a query under other options was refused as `PlanError::IndexOptions`. The new `target::Layout<S>` trait is a target's layout chosen by value, with the index it answers queries through; `Json::new(options)` implements it for `JsonDocument`, and `Plan::value().encrypt_with_layout(Json::new(options))` builds a `ValuePlan<_, Laid<Json, JsonDocument>>` that seals under the options and resolves every query through the plan's own index, so a query does not name the options again. The EQL type has the same by value: `eql_bindings::v4::JsonTree::new(options)` lays a value out as a `JsonTreeDocument` under an identifier.
- **Nothing changes in SQL.** `ord_term` was already NULL for an entry without `op`, and the entry validator already admitted its absence; the functional btree on `eql_v4.ord_term(col -> sel)` indexes the leaves at one selector, which under the opt-in are the leaves of one ordered path.

What remains of the per-path policy is the `vs` half (equality off for a low-cardinality field) and opaque subtrees; neither is scheduled.

## Implementation notes (2026-10-23, Phase 3d: byte encodings and the eight-byte parent tag)

Decision 1 below (the token encoding on the wire) is taken, and the parent tag is shortened with it. The rule is the one "Further mechanisms" set out: a field the SQL compares, derives or decodes must be in an alphabet core PostgreSQL encodes and decodes natively, and only a field the SQL never opens may take a denser one.

- **Every field the SQL reads is padded standard base64**, as `encode(x, 'base64')` writes it and `decode(x, 'base64')` reads it: the selectors `s` and the `s`/`vs` pairs of `q` (sixteen bytes, 24 characters where hex took 32), the parent tag `p`, the ordering term `op` (54 characters where hex took 80), and the tokens and gates `json_tree_subtree_at`, `json_tree_children` and `->` take. `h` already was. The padding stays because `decode(x, 'base64')` refuses the unpadded form (`invalid base64 end sequence`, PostgreSQL 17.10): two characters on a sixteen-byte field and one on an eight-byte one, against a padding step written into every SQL site that would ever decode one. base64url was not taken for the same reason: PostgreSQL has no decoder for it.
- **The ciphertext `c` is RFC 1924 base85** (`base85-simd` 0.1.0: NEON on aarch64, AVX2 on x86_64, portable scalar code elsewhere, wasm32 included), five characters per four bytes against base64's eight per six, on the field that is most of a document. No SQL function decodes `c`. The alphabet has no `"` or `\`, so a JSON string carries it unescaped. `h` stays base64: the SQL reads the `iv` and the sealed-root flag out of it, and it is one field a document.
- **The parent tag `p` is the first eight bytes of its hash.** A parent tag is a lookup key for the server's walk and nothing else: an entry's AAD binds its selector and its ordinal, not its parent tag, so truncation authenticates nothing less. It has to be distinct among the entries of one document only, where eight bytes put a collision in a ten-thousand-node document below one in 10^11. The walk's misses are the other place a short tag could bite: a probe for an ordinal that does not exist that matches some stored tag would return an unrelated entry as a child. A walk of `N` nodes makes about `N` such probes against `N` stored tags, so the chance is the same order, about `N² / 2^64` a walk and row. The row it would add is authentic and opens; the client's rebuild checks each container's child count and each element's position, which catches it in most shapes but not all, so the bound is the probability, not a check. `eql_v4_internal.json_tree_parent_tag` is `encode(substr(h16(…), 1, 8), 'base64')`, twelve characters where hex took 32.
- **`op` needs its own extractor in SQL**, `eql_v4_internal.json_tree_ope_cllw(jsonb)`, because the `ope_cllw(jsonb)` every ordered scalar type shares reads hex and those wires are released. `eql_v4.ord_term` on an entry and on an ordering operand call it; the ordering operators and the functional btree are unchanged.

## Implementation notes (2026-10-23, Phase 4: the planner held to its indexes, and the leakage page)

Two of the three items that gate a release are closed here; the third, the final re-bench, follows them.

- **Planner fragility (gate 2).** `eql_v4.json_tree_query` is plpgsql with `COST 1000` so that a bitmap scan over the GIN index beats a sequential scan even when the documents are TOASTed and the heap looks like a few pages. That was observed in the benches, at 10,000 and 100,000 rows, on one PostgreSQL version, and nothing held it. `postgres_the_planner_picks_the_indexes_without_help` in the encryption suite now does: on a flat table (1,000 four-node documents, every row inline) and a nested table (300 documents of about 220 nodes, every row TOASTed, both regimes pinned by `pg_column_size`), with every planner setting at its default and after `ANALYZE`, containment plans as a bitmap scan over the GIN index and a range at an ordered path as a scan of the functional btree on `ord_term(doc -> selector)`. A control sets the function's cost to 1 for one transaction and shows the planner taking the sequential scan on the nested table, so the assertion is known to be able to fail. The suite runs in `test-eql.yml` in a new `rust-encryption-postgres` job, a matrix over the supported PostgreSQL versions (17 on a pull request, 14 to 17 on a push, like the SQLx jobs); it was a step of the single-version `rust-crates` job. Measured locally on 14, 15, 16 and 17 before the commit.
- **Leakage (gate 3).** `packages/eql/docs/reference/json-tree-leakage.md` is the one page: what a stored row shows at rest, field by field; what each query type hands the database; what is authenticated; the side-by-side with v3 from section 6 above, brought up to date (no `g`, position-keyed `p`, ordering opt-in) and corrected where section 6 was wrong (the entry order; see the note under its table); and the two options that change the picture. It says what a token is and that it is column-wide and does not expire, which is the sentence a customer most needs before sending one.
- **Open for the owner: the stored entry order (2026-10-23, review of #1336).** `sv` and `q` hold the nodes in the walk's order, depth-first, an object's members in the sorted order of their keys (serde_json's `Map` without `preserve_order`; a build that unifies that feature on would store insertion order instead, which leaks the application's field order). Across rows this reveals each row's shape, its parent relation, every array's length and the alphabetical order of sibling key names, which partly undoes what the keyed rank (decision 11) hides from a token holder. The leakage page says so. Closing it is a format change, not a documentation one: a stored order that does not follow the tree (a document-keyed permutation, say, with `j` the permuted position), a rebuild that does not read the tree from the order, and the same for the pairs of `q`, whose nesting would still group array elements. Not taken here.
- **Taken (2026-10-24, #1355, PR #1358): an extracted entry is checked to be the one asked for.** Until then `JsonNode` and `JsonSubtree` opened each entry under the `s` and `j` that arrived beside it, and under the data key the header that arrived with it named. The entry's AAD (`entry_aad` in `packages/stack-encrypt/src/json/derive.rs`) binds the keyset, the column's context, the data key's tag, the selector and the ordinal, and nothing that identifies a row. So a decrypted value was always one sealed in that column, but not necessarily the one at the path asked for, nor one from the row the result puts it in: `->` on `$.salary` could be answered with the row's `$.bonus`, with the sealed root (which opens to the whole document), or with another row's `$.salary` returned together with that row's header. Now a row opens only through what the client derived for the read. `JsonSelector::open(node)` refuses an entry whose `s` is not the selector (another path's entry, and the sealed root, whose selector is the root's, in place of a node) before any key is retrieved. `JsonSubtreeKey::open(rows)` refuses a row that does not fit the key's path: a node a gated walk reaches must carry the path's selector at depth `0`, and the position the path names when its last step is one; every other row must carry the selector of its parent's path extended by its own decrypted label (a key, or the wildcard for an element), which the key derives through the keyset's index-key PRF it now holds; and the rows of each subtree must be consecutive in the document, which is what a subtree is in a depth-first `sv`, so a row out of place, a dropped row and an orphan are refused. A reported depth `d` that disagrees is refused too; the rows are placed by their positions and child counts, not by `d`. The refusal is a new `Error::JsonWrongEntry`, not `Aead` (each entry is genuine) and not `OpenedType` (the entry is not of an unexpected shape; it answers another question). `eql-bindings` follows: `JsonTreeExtracted::from_selector(&selector, entry)` is how an entry `->` returned opens, and `JsonTreeEntry` no longer opens on its own. Still not covered: another row's `$.salary` with that row's header opens, by design (two values sealed under the same context are interchangeable between rows, ADR 0010 in `packages/stack-encrypt/docs/adr`, and row provenance is the database's word); and an array position before the last step of a path reads as the wildcard to every selector, so a walk's rows for `$.a[1].b` can be another element's `b` in the same row. Until the ungated walk returns the node it starts from (#1356), a walk with no gates is also not checked for which node at the path's selector it descends from, which matters only for a token chained through array positions (`$.l[3]`), whose children share every other element's selectors; nor for children left out after the last row it returns, or members left out anywhere, since the node's child count is in the node's own entry and a member's place is a keyed rank. An array's elements are checked to start at `0` (review of PR #1358: leaving out element 0 opened `[10, 20, 30]` as `[20, 30]`), and rows that stop short of a node's subtree are `JsonWrongEntry` like a gap.

## Decisions to take before Phase 1

> **2026-10-22:** these are the open questions as they stood before Phase 1; the implementation notes above record how each was taken. Since then, decision 4's group tags exist only as the nesting of the stored projection `q`, decision 9 was settled by storing the projection (Phase 3), and decision 10's ordinal is not stored (Phase 3b).

1. **Token encoding on the wire:** hex, matching v3's `s`, or base64url, saving about 40 characters per entry. Proposal: measure in Phase 3, default to base64url. Taken 2026-10-23 (Phase 3d): padded standard base64, not base64url, since PostgreSQL decodes only the former; base85 for `c`.
2. **Leaf ordering terms bound to the column only, or to the column and the selector.** Column-only reuses the v4 scalar ordering query domains unchanged and matches the ADR-0009 appendix; selector-bound stops cross-path order comparison at the cost of a JSON-specific query domain. Proposal: column-only for the phased plan, revisit in the ADR.
3. **Array index modes.** Wildcard only, with the chain serving positional access, retiring `[@]` and `[n]`. Proposal: yes.
4. **Group tags on by default**, or opt-in per column for callers who accept the v3 behaviour in exchange for not revealing element grouping. Proposal: on by default; `Contains` is declared exact and that declaration has to be true.
5. **`c` for container nodes**: label and kind only, as proposed, or label, kind and child count (lets the client pre-size and detect a truncated subtree). Proposal: add the child count; it is two bytes and it turns a missing entry into an error instead of a silently shorter array.
6. **Whether to fix v3 too** by porting the group tags and recheck to cipherstash-client and the v3 SQL. Separable; not proposed here.
7. **Plain SHA-256 or HMAC-SHA256 for the token derivations.** Plain SHA-256 is sound as argued under "The token chain": truncation and prefix domain separation each defeat length extension on their own, and no derivation is used as a MAC. HMAC would be an abundance of caution. Decided 2026-10-18: keep SHA-256 for the phased plan, and revisit only with Phase 3 benchmarks over large documents and tables in hand, since the question is whether the extra compression per walked node is measurable, not whether the construction is safe.
8. **The sealed root is a boolean option, on by default; its name is open.** Decided 2026-10-18, see "The sealed root" under the token chain. The two shapes are `d = 0` (chain from the root) and `d = 1` (document at the root, heads at the top-level fields); no other depth is exposed, because `d ≥ 2` leaks subtree sizes at rest and grows storage linearly. Working name "root node obfuscation", which says what it hides; alternatives that say what it stores are `sealed_root` or `root_document`. Phase 3 should measure the root copy against the three document shapes so the default is confirmed by numbers rather than by the estimate above.
9. **Native `@>` over the element-nested projection, built from tags or from a nested `sv`.** Both give identical leakage; the first keeps the flat `sv` every other function reads, the second drops two fields from the wire and changes `->` to a `$.**` lookup. Proposal: projection from tags first, measure both in Phase 2.
10. **Position-keyed parent tags on by default.** They remove sibling linkability at rest for one small integer per entry and `W × F` hashes per walk. Proposal: on, unless Phase 3 shows the walk cost matters on large documents.
11. **Key the label step of the token chain.** As written, a child's token is an unkeyed hash of its parent's token and its label, so whoever holds a token can test guesses of every key name beneath it (see "What a token is" under the token chain). Deriving the step under the index key, `PRF(json/token ‖ column, t(parent) ‖ 0x01 ‖ key)`, closes that at no cost to the server, which unwraps child tokens rather than deriving them. The same holds for anything else the client derives from a label under a token. Proposal: key it. **Where this stands:** the label step is keyed through the member's selector (the 2026-10-24 change below), and a member's ordinal is a random permutation per document (the 2026-10-26 notes), so no keyed rank remains in the format.

## Design change (2026-10-24): derivable tokens, the self tag, and wildcard expansion on the client

**Status:** agreed with the owner on 2026-10-24 and implemented in the pull request stacked on this write-up (see "Plan" below), with the open questions this section first carried settled as "Decisions (2026-10-24)" at its end, which override anything above them. The leakage page (`packages/eql/docs/reference/json-tree-leakage.md`) describes the format after the change, so neither should reach `next` without the other. Tracked in #1360.

### Why

Since Phase 3b a child's token is `t(child) = H16("t" ‖ t(parent) ‖ s(child) ‖ LE32(o))`, where `H16` is the first sixteen bytes of SHA-256, `s(child)` is the child's path selector and `o` is its **ordinal**, its place among its siblings. An array element's ordinal is its index. An object member's is its rank among its siblings: the members are sorted by `PRF(json/rank ‖ column, PAE(t(parent), key))` (`rank` and `shuffled_ordinals` in `packages/stack-encrypt/src/json/derive.rs`, the design's decision 11), so a member's ordinal depends on which other keys the object holds in that row. The client does not know a row's sibling keys, so it cannot derive the token of any node below a top-level field except through array positions (`subtree_key_for`). Everything else this document has had to add to the read path follows from that one fact:

- **Gates exist only for it.** From the first key step below a head, the client stops deriving tokens and sends one gate per remaining step, which the server walks through (`json_tree_subtree_at`). A read of `$.profile.address.city` therefore sends `$.profile`'s token: a capability over that whole top-level field, in every row of the column, for as long as the column lives, to read one leaf.
- **It is why a read could not return the node it names.** A walk finds a node by its parent's token, and a chain head has none, so the ungated walk returned a node's descendants and never the node: `{}`, `[]`, a scalar and a missing field all came back as no rows (#1356). A read of `$.tags[1]` derived the element's own token and so had the same problem.
- **The patch for that widens the leak.** PR #1359 returns the node by sending a head's selector beside its token, and turns a path's last array position into a gate from the array's token (`#n:<selector>`). A read of `$.tags[1]` then sends `$.tags`'s token, which walks every element of that array in every row.

Three changes remove all of it: a member's token stops depending on its ordinal, every entry carries a tag derived from its own token, and the client expands wildcards into concrete paths itself.

### 1. Ordinal-free member tokens

```
t(member)  = H16("t" ‖ t(parent) ‖ s(member))                 object member: no ordinal
t(element) = H16("t" ‖ t(array) ‖ s(element) ‖ LE32(i))      array element: i is its index
p(child)   = H8("p" ‖ iv ‖ t(parent) ‖ LE32(o))               unchanged; o is the stored ordinal
```

`H8` is the first eight bytes of SHA-256, as Phase 3d made the parent tag. Object keys are unique, so a member's selector alone separates it from its siblings, and the ordinal adds nothing to its token but the dependency on the other keys. Every element of an array shares one selector (the wildcard path's), so an element keeps its index. Since an element's ordinal already is its index, an element's token is unchanged. Chain heads and the root derive as today: under the sealed root a head's token is `PRF(json/token ‖ column, path)`, and with the root open the root's token is that PRF of `$` and a top-level field's follows the member rule from it.

**Ordinals stay, for enumeration only.** The parent tag `p` keeps the ordinal, and an object member's ordinal is a uniformly random permutation of its object's members, drawn from the document's generator when it is sealed (`member_ordinals` in `packages/stack-encrypt/src/json/derive.rs`). Enumerating a node's children is still a probe of `o = 0, 1, 2, …` until the first miss, and the ordinals the probe reveals say nothing about the keys, in one row or across rows. Only the token stops depending on it.

**The consequence is the point of the change: the client derives the token of any wildcard-free path from the path alone.** Head, then one hash per step, the step's selector from the path and, for a position, the index from the path. A token sent therefore always covers exactly the node asked for, and the gates have no reason to exist.

**An element and a member still never share a token.** The Phase 3b review (#1329) bound the child's selector into the step so that the token of `$.a[0]` could not be, in a row whose `$.a` is an object, the token of whichever member ranks first. That property holds under the new rule twice over: an element's selector is the wildcard path's and a member's names its key, so the hashed inputs differ; and the inputs have different lengths (33 bytes for a member, 37 for an element), so they differ even if two selectors ever coincided. A member and an element cannot sit under the same parent in one row, and across rows a token for `$.a[0]` finds nothing in a row whose `$.a` is an object, because no entry there carries that token's self tag (next section).

**The server cannot tell which rule a hit takes, and the self tag tells it.** As it walks, the server derives each hit's token from its parent's to go one level further. Today that is one rule for every hit. Under the new rules it needs to know whether the hit is a member or an element, and nothing stored says so: the kind is inside `c`, and a selector is a keyed hash that does not say whether its path ends in a key or a wildcard. So the walk derives the member candidate `H16("t" ‖ t ‖ s)`, keeps it if the hit's stored self tag `x` is `H8("x" ‖ iv ‖ candidate)`, and otherwise derives the element candidate with the hit's ordinal and checks that. A hit whose `x` matches neither is returned but not descended into; the client's check refuses it. That is up to four hashes per hit where the walk spends one today, on top of the two probes per node; the benchmarks below measure it.

**Key names stay out of reach.** A member's token now hashes its selector where it hashed its ordinal. The selector is a PRF under the index key, so whoever holds a parent's token still cannot test a guessed key name: they would need the guess's selector, which takes the index key. Nothing about decision 11 moves.

**The AAD does not change.** An entry's AAD (`entry_aad`) binds the keyset, the column's AAD, the data key's tag, the entry's selector `s` and its position `j` in `sv`. It does not bind the sibling ordinal `o`, the token, `p` or the new `x`, and it need not: the change moves only fields the server derives and compares, none of which is authenticated today.

### 2. A self tag on every entry

```
x(node) = H8("x" ‖ iv ‖ t(node))      stored on every entry: the root, the heads and every node below
```

The self tag lets the server find an entry from its own token, where `p` finds it only from its parent's. It is salted by the document's `iv` like `p`, so at rest it is random bytes that link nothing within a row or across rows until a query supplies a token. It is on every entry, so its presence marks nothing: unlike `p`, which the heads lack, no entry is singled out by carrying it.

**The sealed root carries one.** The root's token is derivable from `$` alone, with the root sealed or open, so the root entry gets `x = H8("x" ‖ iv ‖ PRF(json/token ‖ column, "$"))`. Today a sealed root has no token at all (the walk gives it none, and `json_subtree_key` refuses `$` as `TermError::JsonSealedRoot`). Under the sealed root nothing chains from `t($)`: the heads derive from their own paths and carry no `p`. So the root's token finds the root entry and nothing beneath it, which is the document's ciphertext the budget fallback already returns, and a read of `$` becomes an ordinary read that opens the whole document. The client still does not send `t($)` unless `$` is what is read. With the root open, `t($)` remains what it is today, the whole column's shape, and a read of `$` sends it.

**What a read returns.** The node at depth 0, found by its `x`, then everything beneath it, enumerated under the node's own token. So `{}`, `[]`, a scalar and an absent node come back as an empty object's entry, an empty array's entry, the scalar's entry and no rows: the four distinct answers `jsonb #>` gives, which is what #1356 asks for and the semantics #1359 implements. An entry's ciphertext already carries its kind and child count, so the client tells `{}` from `[]` from the entry alone.

**Collisions.** Eight bytes, like `p`. A probe with a token that names no node in the row matches some stored `x` with probability about `E / 2^64` for a row of `E` entries, per token. A false hit is an authentic entry of the row at the wrong place, which the client's check refuses (section 4), so a collision costs a refused read, not a wrong answer.

**Size.** Eight bytes is twelve characters of padded base64, plus `,"x":""` framing: about 19 characters per entry, against roughly 200 per entry today, so about 10% more stored characters. Random bytes do not compress, so the on-disk share should be about the same. To be measured (section 7).

### 3. Wildcard expansion on the client, and no gates

A path with a wildcard (`$.items[*].price`) names no one node, so it has no token. Today the server resolves the wildcard by walking from the deepest derivable ancestor through a selector gate. After the change the client resolves it: it expands each wildcard step to the indices `0 … N−1` and sends one token per concrete path, plus one **probe** token for index `N` of each array it expands. For `$.items[*].price` that is `t($.items[0].price)` … `t($.items[N−1].price)` and the probe `t($.items[N])`. The probe is the element itself, not the element's `price`, because an element past the bound need not have one.

- **The bound.** `N` defaults to 64, in the spirit of the walk's default budget, and is set by the caller where the read is derived. In a row where a probe hits, an array at that level is longer than `N`, and the read fails loudly with an error that names the bound (and not the path, whose key names can be customer data). It never returns a partial answer. The caller can raise `N`, or read the array itself: a read of `$.items` sends the array's own token, which is honest, because the whole array is then what was asked for.
- **Nested wildcards multiply.** Two wildcard levels send `N²` paths, `N` probes at the inner level and one at the outer: `N² + N + 1` tokens, 4,161 at the default. Each token costs the server one hash per row it scans, so a nested wildcard over many rows wants a smaller `N`.
- **A wildcard head becomes readable.** Under the sealed root, `$[*].x` on a root array was refused, because a wildcard head names no one node. Each `$[i]` is a head with its own token, so it now expands like any other wildcard.

**The SQL.** `json_tree_subtree_at` and its gates are removed. The read is

```
eql_v4.json_tree_subtree(doc, tokens text[], budget integer DEFAULT 64)
```

For each token in turn, it looks the entry up by `x` (one map of the document's entries keyed by `x`, built once per call beside the existing map keyed by `p`), returns it at depth 0, then returns its descendants by ordinal probing under the node's own token, deriving each hit's token as section 1 describes. Rows come out in token order, and within a token in document order. A token with no entry yields no row. `json_tree_children(doc, token)` and `json_tree_child_count(doc, token)` lose their gates and take any derivable node's token: they enumerate one level below it, which needs no child token and so no rule choice.

**The budget.** The walk counts rows across all the tokens of one call, the depth-0 rows included. With the root sealed and the count past the budget, it returns the root entry alone at depth 0, as today. The client opens the root to the whole document and evaluates the same concrete paths and the same probes over it. A probe that finds an element there is the same truncation error the walked read raises, so one row gives the same answer under the budget and over it, which is the property the Phase 3b review (#1329) held the fallback to. The client could answer a wildcard in full from the document, but then the answer would depend on the budget; decision 4 below keeps the bound. With the root open there is no fallback, as today.

**The walk's bound needs rewording.** "The bound" in `functions.sql` argues that no two rows share a token because a hit's token is a hash of its probe, which includes the ordinal. A member's token no longer includes it: two entries forged under one parent with the same `s` and the member self tag would derive one token, and the walk would visit the subtree beneath it twice. The walk's other limit, `LIMIT` the entry count plus one, still caps the rows, and the client refuses a repeated position (`j`) as it does today. The comment has to say so. (Decision 9 below makes the read's limit the entry count times the number of tokens; `json_tree_children` and `json_tree_child_count`, which probe one level, keep the entry count plus one.)

### 4. The client's check after the change

PR #1358 made the client open a walk's rows only through the key it derived and refuse any row that does not fit (`Error::JsonWrongEntry`). It adapts:

- **Each depth-0 row** must carry `x = H8("x" ‖ iv ‖ t)` for one of the tokens sent, and its authenticated selector and decrypted label must agree with that token's path: the path's selector, and the key or index its last step names.
- **Each deeper row** must sit at the next consecutive position `j` within its subtree, carry the selector of its parent's path extended by its decrypted label, and carry an `x` that matches the child token the client recomputes from its parent's token, the row's selector and its label (the key for a member; the index, from the label, for an element). `p` is not checked (decision 8).
- The child counts in each container's ciphertext still catch a dropped row, and a repeated position is still refused.

`x` and `p` are not authenticated. The database holds every token a read sends and every row's `iv`, so it can write any `x` or `p` it likes. Matching them catches a row corrupted by someone who never saw the token, and a server that walks wrongly by mistake, but not a dishonest database. What binds a row to its place against the database is what the AAD covers: the selector, the position `j`, and the label and child count inside `c`. The check that each subtree's rows are consecutive in `sv` is on `j`, so it is one of those, and it stays beside the `x` check (decision 8). Nothing replaces it: the `x` check is a consistency check, and the bound fields with the consecutive-position rule are the security check, as the leakage page says. Decision 8 shows what the rule refuses that nothing else does.

Still allowed by design (ADR 0010, `packages/stack-encrypt/docs/adr/0010-what-a-stored-value-authenticates.md`): an entry swapped in from another row under the same column context, returned with that row's header, opens. Row provenance is the database's word.

### 5. Wire

A stored entry becomes `{s, c, x, p?, op?}`: `x` on every entry, `p` below the heads as now. The domain CHECK on `public.eql_v4_json_tree_entry` and the `JsonTreeEntry` newtypes in `packages/eql/crates/eql-bindings/src/v4/json_tree.rs` gain `x` as padded base64 of eight bytes. Nothing else in `h`, `sv` or `q` changes. Counted informally, this is the format's sixth stored form, "revision 5 to 6"; that is a narrative label only, and no field records it: `JsonHeader::FORMAT_VERSION` stays `1` and the document's `v` stays `4` (decision 5). EQL v4's `json_tree` is unreleased, so nothing stored breaks: every fixture, every pinned vector and every benchmark table is regenerated.

### 6. Leakage after the change

`packages/eql/docs/reference/json-tree-leakage.md` carries the full statement; in short:

- **A subtree read sends exactly the tokens of the nodes asked for.** A read of `$.profile.address.city` sends that leaf's token and nothing that covers `$.profile`. No capability over a top-level field or an array leaves the client unless that field or array is itself what is read.
- **A wildcard read sends `N + 1` tokens for each array it expands**, `N² + N + 1` in all for two levels. The database learns which of them exist in each row, so, up to `N`, which elements hold the rest of the path (each array's length, where the path ends at the element, which the stored entry order already shows, #1357), whether each array is longer than `N`, and the structure beneath each node found. It learns nothing about the elements' sibling fields. One exception: a probe that hits is a token for the element at index `N`, and the server enumerates that element's subtree in each row where it exists, although the read then fails. The exception is in the token, not in what the SQL does with it: whoever holds an element's token can derive that element's subtree in any row, now or in rows written later, so it holds for every variant of the read that sends the element's token (decision 3).
- **Unchanged:** a token is still column-wide and still does not expire; the `->` extraction path and containment send and reveal what they do today; at rest, `x` adds nothing beyond what `p` already shows; and the stored-order disclosure (#1357) is untouched by this change and stays a separate decision.

### Decisions (2026-10-24)

The owner settled the questions this section first left open, before implementation. Where a decision differs from the text above, the decision holds, and the implementation follows it.

1. **Tokens.** `t(member) = H16("t" ‖ t(parent) ‖ s(member))`, with no ordinal; `t(element) = H16("t" ‖ t(array) ‖ s(element) ‖ LE32(i))`, `i` the index; the root's token and, under the sealed root, the heads' are PRFs of their paths, as before. The parent tag `p = H8("p" ‖ iv ‖ t(parent) ‖ LE32(o))` is unchanged, `o` the keyed rank for a member and the index for an element, and is used to enumerate children only.
2. **The self tag, and no kind bit.** `x = H8("x" ‖ iv ‖ t(self))` on every entry, the root and the heads included. Nothing stored says whether a node is a member or an element: when the server enumerates beneath a node and finds a hit at ordinal `o`, it derives the member rule's token and tests it against the hit's `x`, and on a miss tries the element rule's (`eql_v4_internal.json_tree_hit_token`). Up to four hashes per hit; the benchmarks measure what that costs.
3. **Probes are ordinary tokens.** No separate `probes` argument: for each array a wildcard expands the client sends the tokens of the positions `0 … N − 1` and the probe at `N`, the element itself (`t($.items[N])` for `$.items[*].price`). A row at a probe token has an array longer than `N`, and the client fails loudly, `Error::JsonWildcardTruncated { bound }`, never with a partial answer. `N` defaults to 64 (`JsonSubtreeKey::DEFAULT_BOUND`) and is set per read with `KeysetCipher::json_subtree_key_with_bound`; it is a read parameter, not part of the index's options, so the stored form and the data plan do not change with it. Nested wildcards multiply, and a read that would send more than 8,192 tokens is refused before any is derived (`TermError::JsonWildcardTooWide`): every one-level wildcard up to 8,191 elements, two levels up to a bound of 90, never three (the cap was 65,536 until the owner lowered it on 2026-10-25; see the implementation notes below). The exception the leakage page states stands: a probe that hits has the server enumerate that element's subtree, although the read then fails. The exception is in the token, not in what the SQL does with it: whoever holds `t($.items[N])` can find that element in any row by its self tag, probe for its children's parent tags and derive every descendant's token by the public derivations of sections 1 and 2, whatever the function returns, in rows written later too. So a separate argument answered with existence only would not remove it; it holds for every variant that sends the element's token. An existence-only probe needs a different derivation, for example a one-way value such as `H16("e" ‖ t)` sent in place of the token, with each entry storing a tag the server matches from it (beside `x`, or `x` itself derived from it): a change to the stored format and a future option, not this design.
4. **The fallback applies the same bound.** When a read falls back to the sealed root, the client evaluates the same concrete paths and the same probes over the whole document, so one row's answer never depends on the budget, the truncation error included.
5. **No version bump.** `JsonHeader::FORMAT_VERSION` stays `1` and the document's `v` stays `4`; the derivation is edited in place, as the earlier stored forms were. "Revision 5 to 6" above is a narrative label. EQL v4's `json_tree` is unreleased, so nothing stored breaks; every fixture, pinned vector and benchmark table is regenerated.
6. **`$` is a read under the sealed root.** It sends the root's token, which finds the root entry at depth 0, which opens to the whole document. `TermError::JsonSealedRoot` had no other use and is removed; `->` never used it.
7. **Children of an absent node.** `json_tree_child_count` of a token that names no node is NULL (it was 0); `json_tree_children` of one returns no rows. Both take the token of any derivable node. Under the sealed root the root's members chain from nothing, so the root's own token enumerates none: its count is NULL too, not a misleading 0.
8. **The client's check.** The depth-0 row's `s` must be the path's selector and its decrypted label the path's last step (the key, the index, or the root for `$`); each deeper row must sit at the next consecutive `j` within its subtree, with `s` the selector of its parent's path extended by its decrypted label; and every row's stored `x` must be `H8("x" ‖ iv ‖ t)` for the token the client recomputes. The `p` check is dropped. `x` is unauthenticated, so the `x` check is a consistency check that catches server bugs, not substitution; the bound fields `s`, `j` and the label are the security check. The consecutive-position rule is what refuses a node spliced in from under another element of the same array: a read of `$.items[0]` answered with the element's own entry and then `$.items[1].price` in place of `$.items[0].price`, its `x` rewritten, has the right selector, label and child count, and only its position is wrong. Still allowed by design (ADR 0010): an entry from another row, returned with its header; and a node at the same selector under another element when that node is the depth-0 row (`$.items[0].price` served for a read of `$.items[1].price`, with no row before it to fix its position), which no bound field tells apart. Also beyond any check: a database that withholds rows, so that a read opens as no node, or a wildcard read without some elements. The leakage page's "What is authenticated" says all three.
9. **No gates.** `json_tree_subtree_at` is dropped. `json_tree_subtree(e, tokens text[], budget integer DEFAULT 64)` returns, for each token in order, the entry whose `x` matches at `d = 0` and its descendants with `d` their depth below it, in document order within a token. The budget counts rows across all tokens, the depth-0 rows included; past it with the root sealed, the root entry alone at `d = 0`. The recursion is still read through a `LIMIT`, now the entry count times the number of tokens, since forged member tags can make one token's subtree be visited more than once ("The bound" in `functions.sql`). Wanting a whole array is a read of the array's path, which sends the array's own token.
10. **Stacking.** The implementation stacks on this write-up's branch and its pull request targets it. #1345 conflicts with #1358 and merges first.

**Implemented.** The client's reads, checks and the fallback are in `packages/stack-encrypt/src/json/derive.rs`; the key and its expansion in `derive.rs` and `query.rs`; the SQL in `packages/eql/src/v3/json_tree/functions.sql`. The stored form gains `x` and is otherwise unchanged; a sealed document grows by about a tenth in characters (+9.8% on the nested benchmark shape and +9.4% on the flat one, pinned in `packages/stack-encrypt/tests/json_properties.rs`). The derivations are pinned under the deterministic key source in `packages/stack-encrypt/tests/json_tree_vectors.rs`. The PostgreSQL oracle (`packages/eql/tests/encryption/tests/json_tree.rs`) holds every read with no wildcard to `jsonb_path_query_first` in strict mode, wildcard reads to `jsonb_path_query`, the child functions to `jsonb_object_keys` and `jsonb_array_length`, and every read of a randomly tampered row to either the right answer, a refusal, or one of the allowances of decision 8.

### Implementation notes (2026-10-25): what the walk was paying for

The benchmarks of the implementation (cipherstash/benches `report/JSON_TREE_DERIVABLE_TOKENS.md`, summarised on #1363) found the token-specific reads faster than the gated walk and everything that enumerates slower: whole-subtree reads +38 to +46%, a full walk of a 300-element array +78%, `json_tree_child_count` on a small node +59%, with the per-hit cost inside a walk (about 36 µs per member, 80 µs per element) well above what the hashes explain. Reading the plan found four costs, none of them in the format. All four are SQL-only and fixed in #1363; the stored document is unchanged.

1. **A pinned `search_path` disabled inlining of every chain primitive.** The post-install step (`tasks/pin_search_path_v3.sql`) sets `search_path` on every EQL function that does not carry the `eql-inline-critical` marker or take a jsonb-domain argument, and the planner does not inline a SQL function with a `SET` clause. So `json_tree_h16`, `json_tree_le32`, `json_tree_parent_tag`, `json_tree_self_tag`, `json_tree_member_token`, `json_tree_element_token` and `json_tree_hit_token` each ran as a full SQL-function call, about ten microseconds, where the hashes inside cost under one. A level of the walk makes about fourteen such calls, and `EXPLAIN ANALYZE` put the recursive step at 160 µs per level on the 300-wide corpus. The gated walk paid the same way, which is why the derivation's cost was invisible in the first comparison. The seven now carry the marker; the step is 14 µs per level.

2. **`json_tree_hit_token` could not inline even unpinned.** Its body held a `FROM` clause, which blocks inlining; rewritten without one it was still refused, twice: as a STRICT function whose body is a `CASE`, which the planner inlines only when every argument is provably non-null, and then because its arguments, in the recursive term, were the expression that locates a hit, which the planner had flattened into the call, and a function that uses an expensive argument more than once is not inlined. It is now not STRICT, and the walk derives a hit's token where it consumes it, in the probe beneath, from the hit's stored `s` and `x` read off the working table, which are plain columns. An `OFFSET 0` fence on the lateral subqueries also inlined it, but introduced a `Memoize` node keyed on the whole document, at 64 µs per row.

3. **The maps copied every entry, and were built twice.** `json_tree_by_parent` and `json_tree_by_self` each aggregated `elem || {"j": …}` over `sv`, 0.55 ms per map on a 215-entry document, and every read built both; `json_tree_child_count` built them, then called `json_tree_children`, which built them again. One function, `json_tree_index`, now builds both maps as tag → position in one pass (0.14 ms), set-returning with the two maps as columns so the planner inlines it as an aggregate subquery of the caller's `LATERAL`, which is computed once: a scalar function the `doc` CTE named twice (`idx -> 'p'`, `idx -> 'x'`) was evaluated twice when the planner flattened the subquery. An entry is fetched as `sv -> j` only when it is returned.

4. **Every reference to the argument decompressed the document.** The stored value is TOAST-compressed, and the `doc` CTE referenced `e::jsonb` five times (header, `sv`, metadata, entry count, index), each a decompression of the whole document, about 40 µs for a nested one: 0.2 ms of a 0.6 ms one-token read. Each read now takes `e::jsonb #> '{}'`, the identity path, into a MATERIALIZED CTE and reads that.

The `cipherstash/benches` harness measures `json_tree_by_parent` and `json_tree_by_self` as floors; both are gone, so its plan step must move to `json_tree_index` before the next full run.

**For a future version of the format**, recorded here from the review of #1363 (none is in scope for this one):

- *The sealed root's children enumerate from nothing.* The top-level entries carry no parent tag, because the format predates the root having a token, so `json_tree_children` at `$` returns no rows and `json_tree_child_count` returns NULL on the default layout, and a developer counts top-level fields by reading `$` and opening it. Chaining the heads from the root's token, `p = H("p" ‖ iv ‖ t($) ‖ LE32(o))`, would make the root enumerate like every other node. **Decided against for now (owner, 2026-10-25):** a walk from the root is a capability over the whole document's shape that the format deliberately withholds, so adding it increases leakage; SteVec offered nothing like it either, and it waits for a customer to ask.
- *Withheld rows are not detected.* Nothing in a row says how many nodes a read should find, so a database that drops rows makes a node look absent, or shortens a wildcard read. This is an integrity property against a lying database, outside the current threat model (confidentiality against an honest-but-curious one); closing it needs an authenticated count, for instance the array's child count read beside a wildcard.
- *The entries × tokens `LIMIT` and the token cap bound a lying database's own work.* Forged member tags can make a walk visit one subtree repeatedly; the client refuses the repeated positions, so only the database's work is at stake, and with the default sealed root and budget the read stops at `budget + 1` rows regardless. The `LIMIT` is the only bound when the budget is 0 or the root is open, and the token cap (`TermError::JsonWildcardTooWide`) scales it: a one-level wildcard with bound N sends N + 1 tokens and two levels send N² + N + 1, so the cap is 8,192 (owner, 2026-10-25; it was 65,536, which no measurement approached, the largest read benchmarked sending 4,161): every one-level read up to 8,191 elements, two levels up to a bound of 90, the default of 64 included, and no third level.

### Implementation notes (2026-10-26): the cascade, and a random stored order (#1357)

The stored order was the last disclosure of the format that no option changed: entries depth-first, members in key byte order, so a row's sequence of selectors gave its tree exactly, and comparing rows gave the parent of every node, every subtree's size and the byte order of sibling key names. It was deferred because the client's integrity check leaned on it: a read's rows had to sit at consecutive positions below the node asked for, with the position bound into each AAD. The spike in #1371 showed the way out, and the report linked from #1357 the analysis; this is the change, made the format.

1. **The cascade is the integrity rule.** Every entry's AAD (domain `stack-encrypt/json/entry/v2`) binds, beside the keyset, the column, the key tag, the selector and the slot `j`, the digest of its children's AEAD tags, `SHA-256("k" ‖ tag(child₀) ‖ tag(child₁) ‖ …)` in ordinal order, a tag being the last sixteen bytes of a ciphertext as vitaminc lays a leaf out. Sealing runs from the leaves up. A leaf, an empty container and the sealed root (whose members chain from nothing) open under the digest of no children. A node's tag covers its AAD, so it commits to every ciphertext beneath it. Opening a read places its rows the way the server found them, by the chain (the node a token names by its self tag, a node's children by its parent tags at ordinals 0, 1, 2, …, each under the member or element rule its self tag fits), opens each node under the digest of the children placed under it, and then checks it. Nothing reads a slot as a position, so the rows may arrive, and be stored, in any order. Nothing stored changes: the AAD is not stored and the tag is already in `c`. Code: `packages/stack-encrypt/src/json/cascade.rs` and `place` in `derive.rs`.

   What it proves: the rows beneath the node a read names are exactly the ones sealed there, complete, each under its parent and in its place. What it does not: the place of that node itself, which is checked by its selector and its decrypted label alone, since nothing above it is read. The three allowances of ADR 0010 stand (another row's entry; another element's node at the same selector at the top of a read; withheld rows), and ADR 0010 now says so for `json_tree`. Upward verification was weighed in the report and not taken: it needs the ancestors' tokens, which is the capability the token-list read removed.

   Which refusal comes from where. The cipher (`Error::Aead`): a row swapped, dropped, added, reordered or moved under another parent beneath the node read; a truncated or reordered whole document; another column. An entry `->` returned that does not open alone is `Error::JsonNotALeaf`: a container with children (its AAD covers tags `->` does not return) or an altered entry, which nothing outside the ciphertext tells apart, so the error names both and claims neither. The client (`Error::JsonWrongEntry`): rows of two documents and an entry returned twice, before any key is retrieved; a row no token's subtree reaches; a reported depth the chain does not give; a child whose self tag fits neither rule, or not the one its label names; a node at the top of a read whose selector or label is not its path's; the sealed root anywhere but at `$`; a container whose plaintext child count is not the number of children it opened over. The hostile-row tests (`tests/json_read_checks.rs`, the PostgreSQL oracle) assert each of these exactly, and find rows by their paths rather than their slots.

2. **A random stored order is the format.** Not an option, a flag or a switch. The root stays at slot 0, where the sealed-root fallback (`sv -> 0`) finds it; every other entry is placed by a uniformly random permutation of the slots 1…n, and `q`'s pair lists and element groups are shuffled the same way. The permutation is drawn per document at sealing time and thrown away: it is derived from nothing, keyed or not, because nobody needs to recompute it, and a permutation derived from anything stored (the `iv`) would be computable by the database. The generator is vitaminc's `SafeRand::from_entropy` with `next_below` (Lemire's reduction, bias at most n / 2⁶⁴) driving Fisher–Yates (`packages/stack-encrypt/src/json/order.rs`); it is not part of the format, since nothing stored depends on it. For fixtures, `StackCipherBuilder::json_order_seed` (behind `test-support`) draws every document's order from one stream started at a seed, through `SafeRand::from_controlled_seed`, and the deterministic test cipher sets it: `tests/fixtures/json_tree_vectors.json` now pins, per root option, the entries in their stored order, the path stored at each slot, the selector multiset, `q` as sets, and the tokens. The tags and tokens did not move.

   What stays visible at rest, and no order hides: the multiset of selectors (paths, node counts, array lengths, whether two rows have the same paths in the same numbers), `q`'s grouping by array element, which entries are heads under the sealed root (the head count, no longer the size of each head's subtree), each ciphertext's length, and the ordering terms at ordered paths. The leakage page drops its stored-order row and says this; the executable profile in `tests/json_leakage` models the new order, reading every world in an order an observer can rebuild without the stored one (`canonical.rs`). A containment or equality needle is shuffled the same way, with a fresh permutation per query drawn from the same `OrderSource` (`JsonQuery::of_terms` and `at_path`; the seed travels in the query's `JsonTerms`), so the query-time profile matches the at-rest one: in the walk's order a needle would show which of two sibling keys sorts first. `jsonb @>` is set containment over arrays, so the order changes no answer, and `JsonSelectorSet` (and so `JsonQuery`) compares as sets. Added at the owner's request after review, in the same PR.

3. **First match at a wildcard path is unspecified (owner, 2026-10-26).** `json_tree_path_query_first`, and so `->`, `->>` and an ordering on `eql_v4.ord_term(col -> sel)`, returns the first entry in `sv` carrying a selector. At a wildcard path (every element under `$.a[*]`, at any depth) that is now an unspecified element, stable for a stored row but not element 0. Ordering or comparing over the elements of a wildcard path is written over all the matches (`json_tree_path_query`, `EXISTS` or `ORDER BY` over their ordering terms), and element order within a document is recovered after decryption from the labels, as it already was. No SQL changes. Two variants were considered and dropped by the owner: a fix-up after the shuffle that kept each wildcard selector's document-first entry first (it would have revealed, per wildcard selector, which entry is the document-first one), and writing the heads' digest into the sealed root's plaintext so that a client reading the root with its heads could verify them. The sealed root commits to nothing beneath it.

4. **The keyset is loaded on a root-open decrypt.** Opening a whole document whose root is open walks the chain from the root's token, which needs the index key of the keyset it was sealed under. The open asks for it beside the data key, as a kind of request a `Pending` carries (`Request::load_keyset`), answered from the cipher's keyset cache or loaded from ZeroKMS on a miss through the path `StackCipher::keyset` uses; the loads run beside the data-key retrieval, and a load that fails fails only the documents under that keyset (`Error::KeysetLoad`). Settling a pending asks for a `DataKeySource` that is also an `IndexKeySource`, which every `StackCipher` is built over. The sealed root (the default) loads nothing.

5. **An object's member ordinals are a random permutation.** The ordinal `o` in a member's parent tag, `H8("p" ‖ iv ‖ t(parent) ‖ LE32(o))`, which the server probes from zero to enumerate a node's children, was the member's keyed rank among its siblings (decision 11). Nothing reads a rank back: placement probes the parent tags and reads what is there, and a member's token does not depend on its ordinal. So each object's members now get a uniformly random permutation of `0..n` as their ordinals, drawn from the document's generator beside its stored order (`member_ordinals`, `shuffle::ordinals`). A token's holder, who sees the ordinals it probes, learns nothing from them about the keys, and cannot link a key to an ordinal across rows, which a rank under one token allowed. `RANK_DOMAIN` and `rank` are gone; the pinned vectors move in `order` and in each entry's `p` alone, the tags and tokens are unchanged, and the leakage profile's simulator draws per-row member orders (`member_order_shared_across_rows`).

The SQL doc comments that promised "document order" (`json_tree_path_query`, `json_tree_children`, `json_tree_subtree`) now say what each returns: the stored order, ordinal order, and no promised order; no function changed. The benchmarks were not re-run: nothing stored and no SQL function changed. The client's added work is one SHA-256 per container over its children's tags, at sealing and at opening, and at opening the parent-tag probes the server already runs, which replace the position checks.
