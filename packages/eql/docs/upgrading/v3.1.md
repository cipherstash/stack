# Upgrading to EQL 3.1

This guide covers behaviour in 3.1 that callers should know about. Nothing in
it requires you to change any SQL.

## TL;DR

1. Ordered comparisons of block-ORE text values now check every paired term,
   so a malformed term anywhere in a stored value raises, where before it
   raised only if the comparison reached it. Check your `_ore` text columns
   before upgrading —
   [U-001](#u-001-block-ore-text-comparisons-check-every-term).

## Compatibility

| Surface | Status |
| --- | --- |
| Ordering results of every block-ORE operator and the ORE operator class | **Unchanged** for well-formed values. |
| Block-ORE text values (`public.eql_v3_text_ord_ore`, `public.eql_v3_text_search_ore`) with a malformed or mismatched-width term | **Changed.** Every comparison against the value raises — see U-001. |
| Wire format, domains, index terms | **Unchanged.** No re-encryption, no data migration. |

## Upgrade notes

### U-001: Block-ORE text comparisons check every term

**What changed.** A block-ORE text value carries up to six ORE terms. The
comparator behind its ordered operators (`<`, `<=`, `>`, `>=`), `ORDER BY` and
the ORE operator class used to compare term by term and stop at the first
unequal pair. That made its run time reveal how long a prefix two values
share, so it now compares every paired term in a constant number of
operations. A consequence is that every paired term is now checked. A term
that is malformed (its length is not 49 × N + 16 bytes for some N ≥ 1) or
whose width differs from the term it is paired with raises:

```
ERROR:  Malformed ORE term: 407 bytes
ERROR:  Ciphertexts are different lengths
```

Before 3.1 the comparator raised only when it reached the bad term, which it
did not when an earlier term already settled the order, or when the bad term
was paired with a NULL element.

**Who is affected.** Only rows whose `ob` terms were not produced by a
CipherStash client: hand-edited payloads, truncated values, or payloads from
another encoder. Values encrypted by CipherStash clients are well formed, and
single-term domains (every block-ORE domain but text) are unaffected.

**Why it matters.** One bad row can now fail a whole query that orders or
range-scans the column, and `CREATE INDEX` or `REINDEX` on it, instead of
being skipped silently.

**What to do.** Before upgrading, list the term widths in each block-ORE text
column. Every term in a column should have the same width:

```sql
SELECT octet_length(term.bytes) AS bytes,
       (octet_length(term.bytes) > 16
        AND (octet_length(term.bytes) - 16) % 49 = 0) AS well_formed,
       count(*) AS terms
FROM my_table t,
     unnest((eql_v3_internal.ore_block_256(t.my_column::jsonb)).terms) AS term
WHERE term.bytes IS NOT NULL
GROUP BY 1, 2
ORDER BY 3 DESC;
```

One row, with `well_formed` true, means the column is clean. For any other
width, find the rows that carry it and re-encrypt them:

```sql
SELECT t.ctid
FROM my_table t
WHERE EXISTS (
  SELECT 1
  FROM unnest((eql_v3_internal.ore_block_256(t.my_column::jsonb)).terms) AS term
  WHERE octet_length(term.bytes) <> 408  -- the width the first query reports
);
```

## Rollback

Installing the 3.0 bundle restores the term-by-term comparator. Applying any
EQL bundle drops and recreates its schemas, so re-apply grants and dependent
objects afterwards — see
[U-002 in the 3.0.5 guide](v3.0.5.md#u-002-grants-and-dependent-objects-do-not-survive-an-install).
