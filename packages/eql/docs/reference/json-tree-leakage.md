# What an encrypted JSON tree reveals

`public.eql_v4_json_search` (EQL v4) stores a JSON document so that PostgreSQL can answer containment, path extraction, ordering at chosen paths and subtree reads without the key. To answer those queries the database needs some of the document's **structure**: which paths a row has, which (path, value) pairs it holds and which repeat across rows, which nodes share an array element, and lengths. That structure is what this page lists, item by item, with the query capability or storage choice each item pays for. The values stay secret: every value, key name and container sits inside an AES-256-GCM ciphertext under the document's data key, nothing on this page shows the text of one, and the order the nodes are stored in is random per row and shows nothing. `json_tree` reveals strictly less than EQL v3's `ste_vec` ([the comparison below](#compared-with-eql-v3-publiceql_v3_json_search)): no subtree's size, no document order, and no equal ciphertexts for equal values. Read this before you put a column on it, and decide the two options at the end with it in mind.

## What a stored row shows

Someone who holds the column and no key, such as a database administrator, a backup, or an attacker with a copy of the table, learns the following from each row. "Across rows" means a comparison between rows of the same column. No selector, value selector or ordering term links one column to another; the header names the keyset, which is the same for every column it seals.

| field | what it reveals |
|---|---|
| `s`, the path selector on every node | **Which paths the row has, and how many nodes sit at each.** A selector is a keyed hash of the path, the same in every row of the column, so two rows with a selector in common hold the same path. Key names are inside the hash and not readable. Array elements share their array's selector, so `$.tags[0]` and `$.tags[1]` look alike, but each element is its own entry: the number of entries carrying `$.tags[*]`'s selector is the length of `$.tags` (the total over every array at that path, when the path runs through another array). |
| `q`, the containment projection: one `{s, vs}` pair per node, nested by array element, each list in a random order | **Whether two rows hold the same value at the same path**, through the value selector `vs`, a keyed hash of the path and the value (for an object or an array, of its kind alone). So at each path the database sees which rows agree and how often each value occurs: a frequency histogram of every path, and whether one row's document contains another's. Not the value itself, and not whether two different paths hold the same value (the ordering terms below do show that, at the paths the index orders). **Which nodes sit inside the same array element**, through the nesting, for every element that is an object or an array, and which elements sit inside which. That grouping is what makes containment exact for arrays of objects. v3 reveals it too, through its entry order and per-element `a` flag (see the comparison below); here it is explicit in the projection. The pairs of each group and the groups of each list are stored in a random order, so the projection does not restate the document's order. |
| `p`, the parent tag below the chain's heads | Nothing on its own. It is salted by the document's `iv`, so the same position in two rows is unrelated bytes, and it does not say which entry is the parent. Which entries carry no `p` does show: with the sealed root on, those are the root's direct members, so **how many top-level fields the row has**, and which selectors they carry. Not what sits beneath each one: the entries are stored in a random order, so nothing ties an entry to its top-level field. With the sealed root off, only the root lacks one. |
| `x`, the self tag on every entry | Nothing on its own. It is a hash of the entry's own token salted by the document's `iv`, so it is unrelated bytes in every row and links no entry to another, and since every entry carries one, its presence marks none. Given a token, it is how the database finds that token's node in any row. |
| each ciphertext's length, and the number of entries | **The node count**, and for each node the length of its key name (for an object member) plus, for a scalar, the length of its value, exactly, less the AEAD's fixed overhead. A string's length in bytes and a number's length in digits are therefore visible per node. With the sealed root on, the root entry's length is the document's length as JSON. |
| `op`, the ordering term, only on number and string leaves at the paths the index orders | **The order of that leaf's value among every row that holds one, and which rows hold equal values.** The term is order-preserving encryption (CLLW OPE) under one key per column for each kind of leaf, so leaves at two ordered paths compare with each other too, and two ordered paths holding equal values carry equal terms. A number's equality is as a 64-bit float: two different integers past 2⁵³ can round to one float, and then they share a term and tie under `ORDER BY` while their value selectors differ. Strings are ordered and compared after their case and accents are folded, so `"Abc"`, `"abc"` and `"ábc"` get the same term: the equality it shows is of folded values. It is deterministic and not a random value: two values whose encodings share leading bits (for a number, its sign and then its exponent's leading bits; for a string, its first characters) get terms that share leading bytes, one byte per bit, so the term also shows how long that common prefix is, to the bit. So the stored terms alone sort the numbers at the ordered paths into signs and binary orders of magnitude, and show how far into their folded text two strings agree. This is CLLW's known profile; a scheme that hides the prefix is planned for a later version. **Its length is the leaf's length**: one byte per bit of the value's order encoding plus one, so 65 bytes for every number and `8 × (n + 1) + 1` bytes for a string whose folded UTF-8 form is `n` bytes. A term's presence at an ordered path also says the leaf is a number or a string. At an ordered path whose values are numbers in some rows and strings in others, the order between a number and a string depends on the column key and is not jsonb's (jsonb sorts numbers before strings); within each kind the order is the values'. The two kinds' terms are under different keys, so the terms also show which leaves are numbers and which are strings, and the strings sort together, as one block that the key places below the numbers, between the negative and the non-negative ones, or above them. By default no path is ordered; see the options below. |
| `h`, the header | The keyset the data key was minted under, the data key's identifier (unique to the row), and whether the root is sealed. `v` and `i` are the version and the table and column identifier every EQL value carries. |

The entries of `sv` are stored with the root first, where the database finds the sealed root, and every other entry in a uniformly random order drawn when the row is sealed and then discarded. It is not derived from anything stored or from any key, so it is unrelated in every row, two rows sealed from one document included, and it shows nothing beyond the root's place.

Not revealed at rest: any value's or key name's text; except through the ordering terms at the paths the index orders, whether two different paths hold the same value; and, since the entries are stored in a random order, the row's tree as such: no row writes down the parent of a node, the size of a subtree, or which of two sibling key names sorts first.

What stays visible whatever the order:

- **the multiset of selectors**: which paths the row has and how many nodes sit at each, so every array's length, and whether two rows have the same paths in the same numbers;
- **`q`'s grouping by array element**: which nodes share an element that is an object or an array, and which elements sit inside which;
- **the head count** under the sealed root: how many top-level fields the row has;
- **each ciphertext's length**;
- **the ordering terms**, at the paths the index orders.

From these the tree can still be partly inferred across rows: a path never occurs without its parent's, so which selectors occur together suggests which path sits under which, and inside array elements the grouping in `q` says it outright.

## What a query shows

A query hands the database a term derived from the plaintext it asks about, and the database's answer is visible to it. Each query type reveals the following, in addition to the rows it returns.

- **Containment (`@>`, `<@`), and equality at a path, which is sent as a containment needle.** The needle's own projection: the selectors of its paths, the value selectors of its nodes, and its element grouping. So the database learns which paths and which (path, value) pairs you asked about, and which rows hold them. A needle is sent in a random order too, drawn afresh for each query, so it shows no more of the order of the needle's keys than a stored row does.
- **Path extraction (`->`, `->>`, `json_tree_path_query`, `json_tree_path_exists`).** The selector of the path asked. A position in the path reads as the wildcard, so a position is not sent. The entry returned is a ciphertext. At a wildcard path (any path with an array step, at any depth: every element under `$.orders[*]`), `->`, `->>` and an ordering on `eql_v4.ord_term(col -> sel)` take the first entry carrying the selector in the stored order, which is random per row: an unspecified element, the same one every time that row is read, and not element 0. To compare, order or read every element, use the all-match form (`json_tree_path_query`, or `EXISTS` and `ORDER BY` over the matches' ordering terms); a client recovers element order after decryption, from each element's position, which is inside its ciphertext.
- **Ordering at a path (`<`, `<=`, `>`, `>=`).** The path's selector and the bound's own ordering term, which compares with the stored terms exactly as they compare with each other: the database learns the bound's place in the order of the stored values at every ordered path, and whether it equals one. `ORDER BY ord_term(…)` sends no term and shows nothing the stored terms do not.
- **A subtree read (`json_tree_subtree`, `json_tree_children`, `json_tree_child_count`).** A **token** for exactly the node the path names, which the client derives from the path alone. Reading `$.profile.address.city` sends that leaf's token and nothing that covers `$.profile`. No token over a top-level field or an array leaves the client unless that field or array is itself what is read.
  - **A wildcard** (`$.items[*].price`) is expanded by the client into one token per concrete path, up to a bound `N` (64 by default, set by the caller), plus a **probe** token for the element at index `N` of every array a wildcard expands. A probe that finds an element means the array is longer than the bound, and the read fails rather than return part of the answer. So the database learns which of the nodes exist in each row, which shows, up to `N`, which elements hold the rest of the path (each array's length, where the path ends at the element; the selectors already show it), whether each array is longer than `N`, and the structure beneath each node it finds. It learns nothing about the elements' sibling fields. In a row where a probe finds an element, the database also walks that element's subtree, although the read then fails. That exception is in the token, not in what the SQL function does with it: a probe is the element's own token, so the database can find that element in any row, enumerate beneath it and derive its descendants' tokens, in rows written later too, whatever the function returns. It holds for any read that sends the element's token. Two wildcard levels send `N² + N + 1` tokens, `N + 1` of them probes, one at index `N` of each array the read expands: the `N` inner arrays and the outer one.
  - **What a token is.** A capability over the structure of its node's subtree in *every row of the column*: whoever holds it can find that node in any row (through its self tag `x`), see how the nodes beneath it nest, link each one to its parent, and derive the tokens of the nodes beneath. It also learns whether each node beneath is an object member or an array element, and each element's index: nothing stored says which a node is, but to derive a node's token the database tests its self tag against the member rule and then the element rule, and the one that matches says which; an element's index is the ordinal it is found at. An object's members' ordinals are a random permutation drawn when the row was sealed: they say nothing about the members' keys, and a key's ordinal in one row says nothing about its ordinal in another. It opens no value. Tokens are column-wide and do not expire, so a token sent once is useful to the database for as long as the column lives. Send a token to the database in a query and nowhere else.
  - **The root.** A read of `$` sends the root's token, and a read of anything below `$` does not. With the sealed root on (the default) that token covers no document's structure: it finds the root entry, whose ciphertext is the document, and nothing beneath it, since the top-level fields chain from nothing. With it off, the root's token covers every row's whole document.
  - **`json_tree_children` and `json_tree_child_count`** take one token, of any node a path names, and send nothing else. Under the sealed root the root's token enumerates nothing (its count is NULL), for the same reason.

## What is authenticated

Only the ciphertext `c`. Opening an entry verifies that it was sealed under this keyset, for this column, under the data key its row's header names (a fresh one for every row), with the selector `s` and the slot `j` it is opened with, and over the AEAD tags of exactly the children it is opened with: each entry's AAD binds a digest of its children's tags, in order. A ciphertext moved into another row or column, or opened under another selector, slot or set of children, fails. Nothing in it names a row, so an entry that travels with its own row's header still opens; see below. The selectors, the projection, the parent tags, the self tags, the ordering terms, the header's sealed-root flag, and which entries a row holds are not authenticated, by the same rule every EQL stored value follows (ADR 0010 in `packages/stack-encrypt/docs/adr`).

**What a subtree read proves.** A node's tag covers its AAD, so it covers its children's tags, which cover theirs: the tag of a node commits to every ciphertext beneath it. So for a read that returns a node and everything beneath it, the rows beneath that node are exactly the ones sealed there, complete, each under the parent it was sealed under and in its place among its siblings, whatever order the rows arrive in. The client finds where each row should sit from the tags the server uses (the node a token names by its self tag `x`, a node's children by its parent tags `p`) and opens each node over the tags of the children found there; a row swapped, dropped, added, repeated under another parent, reordered or moved breaks a tag on the way up, and the node above it is refused by the cipher (`Aead`). A whole document opened with its root open is checked the same way, from the root down. The sealed root commits to nothing beneath it: its ciphertext is the whole document.

The consequence to design around: tampering with the unauthenticated fields changes **which rows a query returns, where a walk stops, and which entries of a row an extraction or a walk hands back**. An entry the database returns from `->` or a walk carries its own `s` and `j`, and the header it carries names the data key, so a decrypted value is always one that was sealed in this column. The client also checks that what it got is what it asked for, from what it derived for the query, and refuses anything else (`JsonWrongEntry`):

- **`->`.** The entry must carry the selector the client derived for the path. Another path's entry, such as the row's `$.bonus` returned for `$.salary`, is refused, and so is the sealed root returned for a field (it opens to the whole document); the root is accepted only when `$` itself was asked for. A container with children does not open alone, since its AAD covers tags `->` does not return; the client reports that the entry did not open as a leaf (`JsonNotALeaf`), which is also what an altered entry looks like through `->`, since nothing outside the ciphertext says which it was; a container's value is read with a subtree read.
- **A subtree read.** The node each token names, returned at depth 0, must carry that path's selector and, in its decrypted label, the key or position the path ends in (the root, for `$`): nothing above it is read, so these checks are all that place it. Beneath it the cascade places every row. The client also refuses, before the cipher is asked, rows of two documents and an entry returned twice; and after it, a row no token's subtree reaches, a depth the server reports that is not the one the chain gives the row, and a child whose self tag fits neither the member nor the element rule, or not the one its decrypted label names. The self tags and parent tags are not authenticated, and the database holds every token a read sends and every row's `iv`, so it can write any tag it likes: the tags say where to try each row, and the cipher decides. A read of a wildcard whose array is longer than the bound fails rather than return part of the list, both when the rows are walked and when they fall back to the sealed root.

What the checks do not cover, by design:

- **Which row an entry comes from.** Nothing in an entry names its row, so another row's `$.salary`, returned with that row's header, opens; that is the rule every EQL stored value follows (ADR 0010).
- **Which element the node at the top of a read sits under.** Every element of an array shares its selector, and nothing the node binds says which element it belongs to, so a read of `$.items[1].price` can be answered with `$.items[0].price` of the same row (its self tag rewritten), and opens to that element's price. Beneath the top of a read the cascade rules this out; at the top, ruling it out would mean checking the node against its ancestors, which the read does not return.
- **Which nodes a row holds.** Nothing in a row says how many nodes a read should find, so a database can withhold rows: a read answered with none opens as no node at the path (`None`), and a wildcard read answered with some elements' rows left out opens to the rest. That includes a probe's rows, so an array longer than the bound can open as its first `N` elements instead of failing. A node it does return comes with its whole subtree or is refused.

A query's result is not integrity-protected as a whole: each decrypted value is genuine, at a path with the selector asked for and with everything beneath it as sealed, but which row it came from, under which element, and whether anything was left out, is the database's word.

## Compared with EQL v3 (`public.eql_v3_json_search`)

| observer sees | v3 (`ste_vec`) | v4 (`json_tree`) |
|---|---|---|
| which paths a row has | yes | yes |
| which (path, value) pairs a row has | yes | yes |
| node count | yes, two entries per node | yes, one entry per node |
| array lengths | yes | yes, from how many entries carry the element selector |
| size of every subtree | yes: each path entry's ciphertext is the subtree under it | no: no ciphertext spans a subtree and the entries are stored in a random order; the node count at each path is visible |
| parent and child relation | inferable from subtree sizes and co-occurrence across rows | not stored, and not in the order; inferable from which paths occur together across rows, and explicit inside array elements through the projection's nesting |
| whether two rows have the same shape | yes, selectors are column-deterministic | as far as their paths, their node counts at each path and their element grouping go: selectors are column-deterministic, and the stored order is random |
| which leaves sit in the same array element | yes, whenever elements are indexed at all. Entries sit in document order and every element's entry carries the `a` flag (`parent_is_array`), so the leaves between two flagged entries belong to the element before them; with position selectors (`array_index_mode` `position` or `all`) each leaf's selector names its element outright. Only `array_index_mode: none`, the stack's default, hides it, by indexing nothing inside an array | yes, through the projection's nesting, as v3's order and flag do |
| equal values in sibling elements | ciphertexts equal | ciphertexts differ |
| ordering terms | on scalar leaves, with no per-path choice | only at the paths the index orders; none by default |
| a subtree read | reveals the selector asked | reveals a token for exactly the node asked for (one per concrete path, and one probe for each array a wildcard expands), and with it that node's shape in every row for the life of the column |

## The two options that change the picture

- **`sealed_root`** (default on). The root entry's ciphertext is the whole document, so a full read is one decryption and no token a query sends covers a whole document: the root's token finds the root entry and nothing beneath it. The costs are that the root entry's length reveals the document's size, the row is larger, and the root's direct members are marked by their missing `p`, which shows how many top-level fields the row has. Off, there is no document-sized ciphertext, but a read of `$` itself sends the root's token, the whole column's shape.
- **`ordered`** (default none). Each path listed carries an ordering term and takes on the `op` row above; a path not listed cannot be range-queried or sorted, and a query that tries is refused by the client before any key loads. Order only the paths your queries sort or range over.

Neither option changes the stored order: it is random in every row, so it shows nothing of the row's tree (the design document, `docs/plans/2026-10-17-json-tree-index.md` at the repository root, records why).

To report a concern with any of this, see `SECURITY.md` at the repository root.
