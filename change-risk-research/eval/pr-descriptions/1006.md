# feat(stack-prisma): bake EQL 3.0.6 into the migrations

## This PR bakes EQL 3.0.6 into the stack-prisma migrations

This PR adds the migration that installs EQL 3.0.6, and re-emits the baseline so a fresh database installs 3.0.6 too. It must merge before the Version Packages PR, #938.

## The Version Packages PR fails without it

#938 takes `@cipherstash/eql` from 3.0.5 to 3.0.6. Its `Run Tests` jobs fail one `@cipherstash/stack-prisma` test: "the installed @cipherstash/eql release is baked by some published migration (lockstep)". No migration bakes the 3.0.6 install SQL, whose sha256 is `9b6dab78…`. Without this PR, `@cipherstash/stack-prisma` 1.2.0 would depend on EQL 3.0.6 exactly, while `prisma migrate` installed the 3.0.5 SQL.

The 3.0.6 SQL differs from 3.0.5 in three lines, all of them the version: `SELECT '3.0.6'`, `COMMENT ON SCHEMA eql_v3 IS '3.0.6'`, and one doc comment the build writes the version into.

## The baseline re-emit changes nothing that was published

The npm tarballs show that the 3.0.5 baseline re-emit and the 3.0.5 edge never shipped:

- 1.0.0, released on 30 July 2026, ships baseline `fc495f7f…`, plus the 3.0.2 and 3.0.4 edges.
- 1.1.0 and 1.1.1, released on 19 and 20 August 2026, ship baseline `10306543…`, which bakes the 3.0.4 SQL, plus the 3.0.2 and 3.0.4 edges.
- The 3.0.5 baseline and edge reached main in #885 on 21 August 2026, after 1.1.1.

So npm users see the baseline change once, from `10306543…` to `2fdc7caf…`, in 1.2.0. The 3.0.5 changeset already announces that change, and its action applies once.

The team chose to re-emit the baseline rather than add a second `from: null` genesis edge. stack-prisma had 144 npm downloads in September 2026. That is fewer than the roughly 253 a month when the 3.0.5 re-emit was judged safe. A second genesis edge would also add a permanent 2.6 MB copy of the bundle for a release that changes only the version. A second genesis edge is the right shape once adoption is real.

## A 1.1.x upgrade installs the bundle twice

This PR keeps the 3.0.5 edge. The frozen-history test treats committed edges as published, and databases built from main may already have walked it. So a 1.1.x database that upgrades to 1.2.0 walks both the 3.0.5 and 3.0.6 edges, and installs the 2.6 MB bundle twice. That costs time, not correctness. The changeset says so.
