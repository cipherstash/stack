# docs(stack,skills): correct why decrypt/bulkDecrypt skip Date reconstruction

Resolves #779.

## What I found

The issue asks whether the model/raw `Date` split is a bug or a boundary. Investigating both halves separately:

**The behaviour is not wrong.** Every decrypt path on `EncryptionClient` already agrees with its own declared type:

| Path | Declared type | Runtime | Agree? |
|---|---|---|---|
| `decrypt` | `JsPlaintext` (excludes `Date`) | stored string | ✅ |
| `bulkDecrypt` | `BulkDecryptedData` → `JsPlaintext` | stored string | ✅ |
| `decryptModel(row, table)` | `V3DecryptedModel` (includes `Date`) | reconstructs | ✅ |
| `bulkDecryptModels(rows, table)` | `V3DecryptedModel` | reconstructs | ✅ |
| `decryptModel(row)` (table-less, #780) | `Decrypted<T>` → `string` | stored string | ✅ |

That table is scoped to `EncryptionClient` in `client-v3.ts`, which is where the issue points. There are more decrypt surfaces with the same split — four on the `wasm-inline` entry, two on DynamoDB (which reconstruct twice, once via the client and once for aliased v2 paths), Supabase reconstructing itself over the table-less arity, and `prisma-next` with an independent coercion that *throws* on an unparseable value where the core passes it through. None of them contradict the boundary; they inherit or re-implement it.

Reconstructing on a raw path without widening `JsPlaintext` to `JsPlaintext | Date` would make the declared type wrong — which is worse than a documented split. And the single-value half was deliberately pinned in `d5391279` with the rationale spelled out, so this PR takes the documentation branch the issue itself prescribes ("**Alternative, if the boundary is intended**").

**The stated reason is wrong, though.** `decrypt`'s JSDoc said a lone ciphertext "carries no column identity". Verified against the installed `@cipherstash/protect-ffi@0.30.0`: `Identifier` is `{ t: string; c: string }`, documented "**Shared by every payload**" — present on `EncryptedScalar`, `EncryptedSteVec`, and every `eql_v3_*` domain. The identity is there and simply unused. The real constraint is static typing (TypeScript cannot know which column a *runtime* `Encrypted` came from), not a missing runtime capability. The table-less `decryptModel` overload from #780 carried a second copy of the same false claim ("there is no `cast_as` to reconstruct from") — true for an unregistered table, false for a registered one, which is exactly the half @coderdan flagged in the issue comment.

## What changed

No behaviour change. Docs, comments, and two test pins.

- **`client-v3.ts`** — `decrypt` JSDoc rewritten (boundary, consequence, real reason, pointer to the model helpers); `bulkDecrypt` gets its first JSDoc; the table-less overload's justification corrected; the matching runtime comment at the `passthroughRow` site corrected.
- **`wasm-inline.ts`** — same boundary stated on `decrypt` (previously undocumented) and added to `bulkDecrypt`, so the two entries don't drift.
- **`skills/stash-encryption/SKILL.md`** — the `Date`-vs-string consequence in the single-value section, the Bulk Operations section, and both API-reference rows. Includes the "half-works" trap from the issue: comparing two ISO strings orders correctly, so it survives review and breaks later on `.getTime()`.
- **`packages/stack/README.md`** — same correction and note.
- **`__tests__/typed-client-v3.test.ts`** — `bulkDecrypt` was the only path with no test either way (the issue's "Untested either way" retraction covers `decrypt`; #780 covers the table-less model paths). Now pinned, deliberately using a payload whose `i: { t, c }` names a **registered** date-like column, so the test documents that the identity is available and unused.
- **`__tests__/typed-client-v3.test-d.ts`** — the boundary pinned at the type layer too, which is the layer it is argued from: the raw paths must equal `JsPlaintext` exactly. If that union ever gains a `Date` arm upstream, the justification for the split expires and this test fails, rather than the JSDoc quietly going stale.

Incidental cleanup in the unit test file: the client stubs were cast to `EncryptionClient` where `createEncryptionClient` takes the *native* client — a type error at all 12 call sites, invisible because `__tests__` is not typechecked in CI. Now derived from `Parameters<typeof createEncryptionClient>[0]`. 12 type errors → 0.

## The two alternatives, and why neither was taken

**Widen the SDK's own types and reconstruct on the raw paths.** Still available; this PR does not foreclose it. It costs: widening `decrypt` / `bulkDecrypt` to `JsPlaintext | Date` (a compile break for callers annotating `string`), widening `DecryptedFields<T>` from `string` to `string | Date` for the table-less path (`Decrypted<T>` is used in ~30 places, including the DynamoDB operations and `model-helpers`), and deleting the pinned integration assertions at `integration/shared/v2-decrypt-compat.integration.test.ts:542` and `integration/wasm/…:380`. Idempotence (`new Date(aDate)` is a no-op) keeps caller breakage low, so it is a minor, not a major — but it is a release decision, not a doc fix.

**Have `@cipherstash/protect-ffi` return a real `Date` for date-like casts**, as it already returns a native `bigint` for `cast_as: 'bigint'` since 0.28.0, and delete the JS-side reconstruction entirely. This looked like the cleanest fix and was investigated properly. **It does not hold up, for three independent reasons:**

1. **`cast_as: 'date'` is a calendar date, and JavaScript has no calendar-date type.** `packages/stack/src/schema/internal.ts:47-53`: "`date` is calendar-date only (time-of-day truncated to midnight), while `timestamp` preserves the full date+time." Converting `'2026-07-30'` to a `Date` manufactures a time and a zone the stored value does not have — `getDate()` returns the previous day anywhere west of Greenwich. The bigint precedent **inverts** here: bigint was adopted because a JS `number` cannot hold an i64, *removing* loss; a JS `Date` cannot hold a calendar day, so this would *introduce* it, and unrecoverably, in every language binding. ("`Date` for `timestamp` only" is defensible on its merits, but delivers none of the cleanup.)
2. **The JS-side reconstruction is descriptor-driven, not ciphertext-driven, so it could not be deleted anyway.** The SDK repairs from the caller's *current* v3 table descriptor regardless of what is stored — which is what makes a numeric epoch in a date column repairable (`stack-supabase/__tests__/supabase-v3-builder.test.ts:1136`), and what makes EQL v2 payloads read through a v3 descriptor work at all (`v2-decrypt-compat.integration.test.ts:309`: applied "REGARDLESS of the payload's wire version"). An FFI keyed on the stored `Plaintext` variant covers none of those. The change would be additive, not a replacement. `reconstructDatePaths` is also published via `adapter-kit`, so removing it is a major bump independently.
3. **Upstream already stringifies dates deliberately.** `%Y-%m-%d` and "writing rfc3339 datetime to string should never fail" are in protect-ffi's wasm string pool as far back as 0.27.0, and the Rust `Plaintext` enum carries a `Date` variant that the published TS union does not expose. This was decided, not overlooked.

Two further objections, for the record: the raw-value-on-unparseable behaviour is a deliberate, changeset-announced, minor-bumped contract, and `prisma-next` *throws* on the same input — three incompatible policies exist today, and moving the decision into Rust removes every adapter's ability to choose. And nested JSON dates would remain strings structurally (as nested bigints already are), moving the inconsistency from "which method you called" — documented and opt-in — to "which column kind the field lives in, same row", with no opt-out.
