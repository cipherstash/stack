EQL v4 `json_tree` (unreleased): every subtree read now returns the node it names, so an empty object, an empty array, a scalar and a missing field are four different answers, as `jsonb` gives them. The walk for a top-level field, `eql_v4.json_tree_subtree`, returned the field's descendants and never the field itself, because a walk finds a node by its parent's token and a top-level field has none; so `{}`, `[]`, `"text"` and no field at all each came back as no rows. **SQL signature change:** `json_tree_subtree(doc, token, budget)` becomes `json_tree_subtree(doc, token, selector, budget DEFAULT 64)`. The extra argument is the field's selector, the same one `->` takes for the path: the walk returns the one entry with no parent tag that carries it, at `d = 0`, before its descendants, and returns nothing when the document has no such entry. `json_tree_subtree_at` is unchanged and still returns the node its gates reach at `d = 0`; both now run one internal walk, `eql_v4_internal.json_tree_walk`. No stored field was added. In Stack Encrypt a subtree key for a path that ends in an array position (`$.tags[2]`) now walks from the array's token through a position gate, so the element itself comes back; `JsonSubtreeKey::selector()` is what `json_tree_subtree` takes. In `eql-bindings`, `JsonTreeSubtree` opens to the node's own value, and to `Option<Value>`, which is `None` where the row has no node at the path. What the database learns: the selector sent beside a top-level field's token is the one `->` sends; a path ending in an array position sends its array's token, which covers every element of that array, as a wildcard read already does.
